## 1. 这张地图在 BioTrace 里到底干什么

先把功能面压到真实需求（第 2 步已定的），避免按「导航 App」选型。

| 必须有 | 明确不要 | 可后置 |
|--------|----------|--------|
| 把带 GPS 的观察点画在世界地图上 | 录 GPS 轨迹 | 离线整包下载 |
| 按用户自建「旅途」筛选点 | 点与点连线成路径 | 复杂路网导航、公交 |
| 点开 → 照片 / 识别结果 | 驾车导航 | 三维地形炫技 |
| **国内 + 海外**同一套可用 | 只服务中国 | 极致国内 POI/路况 |

**功能量级**：散点图 + 筛选 + 点详情。  
引擎要的是「稳定、免费/便宜、全球坐标一致」，不是「最好的中国路网」。

## 2. 决策框架：五条互相拉扯的轴

选型不是选一个品牌名，而是在下面五轴上找可接受的折中。

```text
① 地理覆盖     全球统一 ←————→ 中国体验极致（海外另说）
② 坐标系      跟照片 WGS-84 一致 ←————→ 跟国内图商 GCJ 对齐（要纠偏）
③ 钱          署名/$0 ←————→ 有免费档但超量计费 / 要 Key
④ 可靠性      捐赠公共实例（无 SLA）←————→ 商业托管（有额度/账单）
⑤ 端形态      先 Web 原型 ←————→ 原生 / 跨端（影响 SDK 选型时机）
```

**本项目硬约束会压死一些轴的一端：**

- 硬需求「必须海外」→ ① 不能选「只做高德中国」当唯一底图。  
- 照片 EXIF 是 WGS-84 → ② 选国内图商当唯一底图，就要长期做偏移与双坐标心智。  
- 非营利、尽量不花钱、个人低频 → ③ ④ 更偏署名免费或高免费额度；可接受无 SLA（不是外卖高峰系统）。

所以框架结论不是「MapLibre 行不行」，而是：

> **在「全球 + WGS-84 + 尽量 $0 + 散点够用」约束下，OSM 矢量系是结构上的主战场；国内图商是「中国标注增强」支线，不是主底图默认解。**

## 3. 必须拆开的两层（否则会混谈）

| 层 | 问题 | 可选空间 |
|----|------|----------|
| **A. 引擎 SDK** | App 里谁负责手势、相机、Marker、点点击？ | MapLibre / Mapbox SDK / 高德 SDK / Google SDK / Leaflet(Web)… |
| **B. 底图数据** | 山河道路标签从哪拉瓦片？ | OpenFreeMap / 自托管 OSM 瓦片 / MapTiler / Mapbox / 高德 / Google… |

可以 **A 开源 + B 公共免费**，也可以 **A 开源 + B 商业**，或 **A/B 都绑同一家**（高德、Mapbox）。  
混谈「用地图」时，容易把「SDK 贵不贵」和「瓦片稳不稳」搅在一起。

## 4. 结构性分叉（真正要辩论的点）

### 分叉 1：一套全球底图，还是「中国一套 + 海外一套」？

| | 一套全球（OSM 系） | 双底图（国内图商 + OSM/Google） |
|--|-------------------|--------------------------------|
| 开发 | 简单：一种坐标、一种样式 | 边界切换、两套 Key、两套标注逻辑 |
| 海外 | 天然满足 | 满足，但复杂度换来的 |
| 国内观感 | 中文标注/POI 常弱于高德 | 国内可更「熟」 |
| 和本项目 | 匹配「单 App、少运维」 | 只有当你**强烈不满** OSM 国内观感时才值得 |

### 分叉 2：钱与可靠性怎么换？

| | 捐赠公共瓦片（如 OpenFreeMap） | 商业免费档（MapTiler/Mapbox 等） | 自托管瓦片 |
|--|------------------------------|----------------------------------|------------|
| 钱 | 通常 $0 + 署名 | 有月配额，超了要钱或降级 | 服务器/硬盘/更新 |
| 风险 | 项目停更、变慢、政策变 | 账单与配额心智 | 运维你来 |
| 适合 | 个人/原型/低频 | 要「合同感」时 | 流量大或公共实例不可用时 |

个人旅行散点：**公共免费实例的风险形态，通常可接受**；不等于「生产级 SLA」。

### 分叉 3：第一版要不要离线？

| 要离线 | 不要离线 |
|--------|----------|
| 野外无网还能看自己的点 | 实现与包体明显变重 |
| 要预下载区域/矢量包 | MVP 只依赖当时有网 |

与「旅行中偶发看图」有关，但**不是识别/相册主路径的阻塞项**。

### 分叉 4：端形态何时绑死 SDK？

| 现在就定 Flutter/RN/原生 | 先定「地图能力契约」 |
|--------------------------|----------------------|
| 可立刻选具体 SDK 包名 | 只定：WGS-84、矢量样式 URL、Marker API、点击回调 |
| 讨论易滑向第 4 步 | 第 3 步保持组件层，不提前写技术方案 |

**框架建议**：第 3 步先定 **A/B 层的约束与倾向**；具体「用哪个跨端框架」放到第 4 步，除非某 SDK 只存在于某一端且会否决其它端。

## 9. MapLibre 是什么（引擎层）

和 OpenFreeMap **不是同一类东西**：

| | OpenFreeMap | MapLibre |
|--|-------------|---------|
| 角色 | **底图数据/样式服务**（瓦片从哪来、长什么样） | **地图引擎 SDK**（App 里谁负责缩放、旋转、画 Marker、点点击） |
| 类比 | 电视节目信号 / 频道内容 | 电视机本身 |
| 你已满意的 | 公共样式 `liberty` 等画面 | （引擎本身几乎「看不见」，除非卡顿或缺功能） |

更具体一点：

- **MapLibre GL JS**：网页里用的引擎（你本地四宫格 demo 就是它在跑）。  
- **MapLibre Native**：手机 App 用的引擎（iOS/Android；也有各类跨端绑定）。  
- 出身：Mapbox GL 开源分支；**BSD**；**不按次收 SDK 费**。  
- 吃的是「样式 JSON + 矢量瓦片」——OpenFreeMap 给的正是这种；所以二者常成对出现。  
- 你在地图上要的「观察点 Marker、点开看照片」由 **引擎 API** 画；底下的山河道路是 **OpenFreeMap 瓦片**。

官网：https://maplibre.org/

没有 MapLibre（或同类引擎），OpenFreeMap 只是一堆瓦片 URL，手机上不会自己变成可交互地图。

## 10. 离线地图：多大？有没有更好？

先分清两件「离线」：

| 类型 | 含义 | 体积 |
|------|------|------|
| **A. 你的观察数据离线** | 照片、坐标、识别结果存在手机 | 跟相册一样，和底图无关 |
| **B. 底图瓦片离线** | 没网也能拖出道路/地名底图 | 才是下面说的「离线地图包」 |

OpenFreeMap **在线看**不需要下载包。若要做 B：

| 范围（矢量、常见 z≈0–14 量级） | 体积粗量级 | 适不适合塞进手机 |
|--------------------------------|------------|------------------|
| 一座城市 / 一小块旅行区域 | 大约 **几十～几百 MB** | 可选下载，合理 |
| 一个国家（中等） | 大约 **数百 MB～1–2 GB** 常见报道量级 | 要用户主动下 |
| **整颗地球**（OpenMapTiles/OFM 全量） | **几十 GB 级**（OFM 还提供整星 Btrfs/MBTiles 周更，偏服务器自托管） | **不适合**当 App 默认离线包 |

### 10.1 用户硬感受：「到新地方打开不能是灰色的」

这和「下载某国精细离线」要拆开：

| | 精细区域离线 | **常驻大概底图（防灰屏）** |
|--|--------------|----------------------------|
| 目的 | 没网也能看清街道/村路 | 一打开就有大陆/国家/海岸线，世界是「活的」 |
| 第一版 | **不做**（已定） | **要做**（用户不可接受灰屏） |
| 典型做法 | 按 bbox 下 z0–14 | **预置或首次下载低缩放世界包**（约 z0–z6/z8），或 App 内置 Natural Earth 类简易全球层 |
| 体积粗量级 | 城：几十～几百 MB | **全球低细节：常见约数 MB～几十 MB**（视缩放上限与矢量/栅格） |
| 新城市街道名 | 有包才有 | **仍依赖在线** OFM；有网后细节叠上来 |

产品语义（写入需求侧）：

1. **冷启动 / 无网 / 瓦片失败**：至少看到「大概的世界」（陆地、国界级/海岸线、大地名量级），**自己的观察点仍能钉在正确位置**。  
2. **有网**：OpenFreeMap 正常出街道路与标注（你已满意的观感）。  
3. **不承诺**：没下过精细包时，陌生小镇的巷道名离线可读。

实现落点留第 4 步（内置栅格层 / 低 zoom MBTiles / MapLibre 缓存预热等），第 3 步只锁定**体验约束**。

结论汇总：

- 第一版：**不做**按城/按国精细离线下载。  
- 第一版：**要**防灰屏的常驻大概世界底图（小体积）。  
- 细节底图：默认在线 OpenFreeMap。

## 12. 结案变更：底图改为天地图（2026-08-10）

### 推翻理由（合规，非观感）

§11 第1 条是按**观感与成本**结案的，当时未评估合规。实际问题：

**OpenFreeMap 使用 OSM 数据，地图上台湾被标成国家级要素**（大字、与他国同级字号）。这在中国大陆法规下属国界与地名表达不合规。这是数据源问题，**换渲染引擎不解决**；fork style 打补丁只改观感、不构成合规，且是需长期维护的技术债。

因此底图改为**天地图**（自然资源部主管、国家基础地理信息中心承办，官方审核版本）：

- 以标准 OGC WMTS 接入，**MapLibre 保留**（§11 第 3 条不受影响）
- `vec_w`（矢量底图）+ `cva_w`（中文注记）双raster 叠加，**必须 `_w` 后缀**（EPSG:3857）
- CGCS2000 ≈ WGS-84，民用精度下**无需坐标转换**，EXIF 坐标直接可用
- 个人非商用免费；需申请两个 key：**浏览器端**（瓦片，配域名白名单）+ **服务端**（逆地理编码）

### OpenFreeMap 的新定位：回落底图

不再是主底图，保留为回落值（`VITE_TIANDITU_KEY` 未配置时启用）。**这直接服务于 §10.1「不能灰屏」那条约束。**

### 换底图后的验证结果（2026-08-10，浏览器实测）

- **原始问题已解决**：台湾在天地图上显示为与大陆同级的省市/县城标注（台北市、台中市、花莲县+ 小圆点），**未见与「日本」「菲律宾」同级的国家级大字或国家符号**
- 底图与中文注记双层正常出图；attribution 显示「天地图 · 国家地理信息公共服务平台 | MapLibre」
- 无 MapLibre style/source 报错；天地图瓦片全部 200，无 403（域名白名单对 `127.0.0.1:5173` 有效）
- `fitBounds` 的 `duration: 0` 生效（无飞行动画）；用户主动缩放上限 14
- **运行时回落已实测**（故意填无效 key）：出现 403 后约 0.7 秒打出 warn、0.8 秒切到 OpenFreeMap 正常出图，**无灰屏**，attribution 自动变为 OpenFreeMap 署名 → §10.1「不能灰屏」这条约束**已由代码保障**
- **仍缺**：审图号原文（`MapPage.tsx` 里留有 TODO），attribution 目前只有平台名。**已决定延后**，但已列入 [`OPS.md`](../OPS.md) 的上架前必办项

### 对 §10.1「防灰屏」的影响：变得更紧要

天地图瓦片配额 **10000次/日为硬墙，超量当天直接拒绝访问、次日恢复，个人开发者无付费提额途径**。也就是说，换底图把一个**无配额**的源换成了**有硬墙**的源——而配额耗尽的表现恰好就是 §10.1 明确不接受的灰屏。

由此确定三种回落触发（性质不同，不可混为一谈）：

| 触发 | 判断时机 | 状态 |
|---|---|---|
| 未配 key | 构建时（`VITE_TIANDITU_KEY` 为空） | 已实现 |
| **瓦片请求失败**（配额耗尽 / 403 / 网络） | **运行时**，监听 MapLibre tile error | **已实现**（2026-08-10）：累计失败达 `TILE_ERROR_LIMIT = 6` 即 `setStyle` 切 OpenFreeMap，单向不自动切回 |
| 视口完全在境外（省配额 + 海外观感更好） | 运行时，按视口 | **不做**（实测配额充足，见下） |

运行时降级**必须可观测**（日志 + attribution 随数据源变），否则可能长期静默跑在不合规底图上，使合规改造失效。

实现说明（`apps/web/src/pages/MapPage.tsx`）：

- 阈值取 6 的理由：一屏双层约 16~32 个瓦片，偶发一两个失败不该触发切换；真正的配额耗尽/白名单失效会让整屏失败，很快越过该数
- MapLibre 的 error 事件在瓦片失败时带 `sourceId`，但**类型定义里没有该字段**，需结构化读取。**无 `sourceId` 时仍计数**——此刻无法区分来源，而漏切的代价是灰屏
- `Marker` / `Popup` 挂在 map 而非 style 上，`setStyle` 不会清掉观察点；attribution 来自 style/source，切换后自动改为 OpenFreeMap 署名
- 回落时 `console.warn` 留痕，含失败次数、HTTP status、可能原因、以及「OSM 数据境内不合规仅兜底」的提醒

### 关于分叉 1「双底图」的重新评估 —— **实测后判定：不采用**

§4 分叉 1 当初否决双底图的核心理由是「边界切换、两套Key、两套标注逻辑」，其中最重的是**两种坐标系**。**在「天地图 + OpenFreeMap」这个组合下该理由不成立**：CGCS2000 与 WGS-84 民用精度等价，OpenFreeMap 也不需要 key。

其潜在收益：合规风险本就集中在中国及周边的边界/地名表达，境内用官方底图正好覆盖要害；海外浏览不消耗天地图配额；海外观感 OSM 本来优于天地图。

**但实测显示配额并不紧张（2026-08-10，Edge + CDP，`Network.setCacheDisabled` 模拟新用户）：**

| 场景 | vec_w | cva_w | 合计 |
|---|---|---|---|
| 首屏 | 9 | 9 | 18 |
| 一轮典型浏览（平移 3~4 次 + 放大缩小各 2 级） | 32 | 32 | 64 |

两层各有独立的 10000/日配额，消耗对称，故瓶颈为单层约 **32 次/完整会话 → 约 300 次完整会话/日**。对个人非商用、日活个位到十位数的项目，余量在两个数量级以上。另外瓦片带 5 天浏览器缓存，重复访问同一区域不再消耗。

**结论：不引入双底图**——为省一个用不掉的配额去背「视口横跨国境用哪套」的复杂度不值得。运行时失败回落已足够兜住极端情况。

若日后用户量级或使用方式显著变化（例如公开注册、大量新用户首访），再按上表重新采样评估。

### 同时判定：不做 Natural Earth 前端兜底层

§10.1 曾列「App内置 Natural Earth 类简易全球层」作为防灰屏手段之一。鉴于运行时失败回落已实现、且配额余量充足，**暂不实现**该层——它要多背一份前端数据与渲染逻辑，收益重复。

（注：后端国别判定已使用 Natural Earth 数据，见 `apps/api/data/geo/`，与此前端方案无关。）
