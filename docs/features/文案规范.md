# 文案规范

> 本项目**唯一**的文案规范。2026-09-14 由 `文案语感基准.md`（已删）与 `文案分区.md`（已并入）合并而成。
> 立规原则：**规则越少越好**。旧规范多是踩坑堆出来的；堆多了，agent 只会「处处遵守」，写出来反而更蹩脚。

## 一、用户可见文案必须落术语表

面向用户的中文（及日后其它语言）**必须**落在 [`packages/messages`](../../packages/messages)（主表 [`packages/messages/src/zh.ts`](../../packages/messages/src/zh.ts)），经 `t()` / `formatRank()` 使用。

- 新增或改 UI 文案：先加/改 message key，再在 Web / API 引用 key。
- 状态名、按钮、空态、错误提示、确认语、稀有度标签、结算文案等同理。
- API 返回给前端的用户可读错误：优先稳定 **code**，由 messages 翻译。
- **禁止**在 `apps/web` / `apps/api` 业务代码里直接写死用户可见中文句子（日志、内部注释除外）。
- 例外：模型 Prompt、开发者日志、纯技术错误原文（落库前应尽量映射为 code）、用户自己输入的内容。
- 改主表或 voice 覆盖表后**必须**跑 `pnpm check:copy`。

## 二、分区机制（固定区 / 可文案区）

> 机制来源 2026-09-04 拍板。界面功能文案分两类，中间隔着机器闸门，不是靠理解区分。

**为什么要分**：皮肤 voice（叙事说法）能覆盖界面文案，但不是所有文案都该被包装——「N · 常见」改成「小清透」会让稀有度跨页面对不上；确认语是防误删闸门。所以分两区，**固定区永远不被 voice 换说法**。

**判定三问**（任一命中即固定区）：

1. **换了说法，功能指代会模糊吗**——稀有度档位、状态名、阶元词、排序标签这类概念锚点
2. **它是事实 / 合规 / 数据的表述吗**——法规定义、科学阶元、审图号、错误码译文、套册内容
3. **它在安全或后果说明路径上吗**——删除确认语、解散后果、危险操作提示

三问都不中、纯场景与情绪包装的，归可文案区。另：`admin.*` 全区固定。

**四道闸门**（机器强制）：

| 闸 | 位置 | 拦什么 |
|----|------|--------|
| 结构闸 | `zh.ts` 拆 `zhCore` / `zhFlavor` 两个对象 | 新增文案被迫二选一，放错区一眼可见 |
| 类型闸 | `ThemedMessageKey = keyof typeof zhFlavor`；voice 表类型 `Partial<Record<ThemedMessageKey, string>>` | 覆盖固定 key 直接编译报错 |
| 运行时闸 | `t()` 内 `themedKeys.has(key)` 判定 | 动态拼 key、js 侧绕过 |
| 校验闸 | `scripts/check-voice.py` | 覆盖表 ⊆ 可文案区；占位符保全 |

**加新文案流程**：

1. 按三问判定归属区
2. key 加进 `zhCore` 或 `zhFlavor` 对应位置（**不要**只加进合并后的 zh——两区物理分开）
3. 跑 `python scripts/check-voice.py` 自检

## 三、术语口径

- 树上的收录物统一「**收录**」：`tree3d.statGot`「已收录 {count} 项」等；nav 仍叫「图鉴」——那是页面名，树上叫收录是动作与状态。
- 量词：点亮族用「格」，册族用「本」，树上条目用「项」。
- 「项」vs「种」：树上节点不全是种（科、目也计数），保留「项」不冒充「种」。

## 四、新增文案两条硬约束（2026-09-10 用户拍板）

**一、先查能不能复用 common，不许直接新建。**
新文案先在 `zh.ts` 的 common 区（及已有同义 key）搜一遍——「返回」「加载失败」「保存失败」「无数据」这类通用说法一律复用，不要为单个页面再造一个。

**二、不做无意义兜底。**

- 上游**必填**的字段，不为它写兜底文案。
- 兜底**只留一种情况**，不为多个可能场景各写一条。
- 不为「分型」写多套 key，除非分型对用户有**信息增量**。
- 判定口诀：**这个分支用户真能看到吗？看到了会因此做不同决定吗？** 两问皆否 → 合并或删。
