# 文案撰写规范

> 文案的**撰写**规则：用哪个词、什么该写什么不该写。**不是工程机制**——key 落位、分区与闸门见 [`文案工程规范.md`](文案工程规范.md)。
> 立规原则：**规则越少越好**。旧规范多是踩坑堆出来的；堆多了，agent 只会「处处遵守」，写出来反而更蹩脚。
> **先分文本类型，再套规则**——两套规则适用范围不同，混用会把句子写死。

## 〇、先分文本类型

| 类型 | 例子 | 用哪套 |
|---|---|---|
| **功能性文本** | 按钮 / 标签 / 状态 / 提示 / 错误 / 空态 / 说明 | 第一套 |
| **创作类文本** | 品牌句 / lede / 叙事句 | 第二套 |

**分错类型的代价**：拿功能性纪律（去句号、禁同义反复、亲切短句、存在意义三问）去审 slogan / lede，
会把句子审死——功能性纪律管的是「把话说准、说短、说清」，创作要的是「说得美、说得让人向往」。

## 一、功能性文本规则

1. **去句号**：按钮 / 标签 / 状态 / 短提示不带句号；完整句子（多段各自独立的信息）该带就带。
2. **禁同义反复**：一句话里两次说同一件事，删一次。
3. **亲切短句优于完整陈述**：短、口语、直给，别端着。
4. **存在意义三问**：说明性文案过三问——① 能据此行动吗 ② 成功时是废话吗 ③ 失败时已有另一条在说吗。皆否 → 删。
5. **事实正确 ≠ 需要告诉用户**：属实只是「可以写」的必要条件。
6. **与界面已有元素重复的文字删**。
7. **不做无意义兜底**：上游**必填**的字段不为它写兜底；兜底**只留一种情况**，不为多个可能场景各写一条；不为「分型」写多套 key，除非分型对用户有**信息增量**。判定口诀：**这个分支用户真能看到吗？看到了会因此做不同决定吗？** 两问皆否 → 合并或删。

## 二、创作类文本规则

1. **不套功能性规则**：上面七条一律不适用于品牌句 / lede / 叙事句。
2. **夸用户，给更大的自我**：文案该让用户觉得自己更大（「行遍山海」），不是缩小他（「行遍家门口的小河」）；不质问用户，不用反问。
3. **别大白话**：避开说明文腔、格言腔、广告腔——「见过世界的人，认得生命」是说明文，「你认得的世界才是你的世界」是格言，都不算文案。
4. **不硬塞产品词**：没本事把功能写美，就别硬塞（图鉴 / 识别 / 拍照）；宁可整句不提产品。
5. **不拿关键词拼贴当写作**：不把品牌语料抠成几个词（遇见 / 名字 / 图鉴）排列组合。
6. **事实底线是「不虚假宣传」**：不是「覆盖所有失败分支」；修辞放大是本职，不是撒谎。
7. **效果第一**：以上都是底线，不是天花板；先像一个牌子在说话，再确保它没撒谎。
8. **别把界面动作说成事物的本质**：「起个名字」是创建流程里的一步，不等于「旅途」本身——把它抬成事物（「起个名字，就有了」），既失真又轻佻。同理，「换个底色」不等于「换个地方看照片」、「换个光」也不等于「把照片再看一遍」。
9. **调子跟定稿 slogan 同族**（正面方向，2026-09-14 用户确认）：**短句对句、有气魄、给用户分量**。已定稿的例子——`app.tagline`「识尽众生，山海入怀」、`trips.lede`「所行之处，皆归于此」、`trips.empty`「还没有旅途。山海未远，等你启程」。反例：平铺直叙的说明句（「你的每一趟旅途，都在这儿。」）——它只是复述了这页是什么，不算创作。

## 三、术语口径

- 树上的收录物统一「**收录**」：`tree3d.statGot`「已收录 {count} 项」等；nav 仍叫「图鉴」——那是页面名，树上叫收录是动作与状态。
- 量词：点亮族用「格」，册族用「本」，树上条目用「项」。
- 「项」vs「种」：树上节点不全是种（科、目也计数），保留「项」不冒充「种」。

## 四、通用

- **判据用于淘汰，不用于生成**：上面所有规则都是尺子，只在筛稿时用；造句时把它们放下。
- **提案至少覆盖「该删 / 该合并 / 该改措辞」三类**（审查方法，只改措辞等于没审）。
