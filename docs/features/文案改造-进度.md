## 维护方式

每过完一个模块：更新该行「状态」与「提交」；有改动的，在「备注」写一句改了什么。
演示页（`prototypes/clear-tree/`，不提交）与该模块同批产出，供拍板。

**提案呈现方式（2026-09-14 用户定）**：**保留的也要逐条展开**（`key · 文案 · 渲染点 · 判断依据`），用户要能审到每一条；改动照旧展开（现状 / 建议 / 理由）。
保留项**按类别分组**（锚点/导航词、技术字段名、状态/反馈、创作类…），用户认可这个分类方式，往后沿用。

**已落地的模块页要标「状态：已落（提交号）」**（2026-09-14 用户反馈）：改完并提交后，那一页就是**记录**，不再按「现状 / 建议」的待批格式重述；汇报时也不重列已落的改动。

**「自己想」= 自己写稿，不是自己定稿**（2026-09-14 用户澄清）：稿子由 agent 写（不再铺一堆候选让用户挑，也不推给别的模型），但**必须拍板后才动生产文件**（纪律 9）。未拍板就改并提交＝违规，要主动认、并给出回退路径。

## 纪律（沿用，用户立）

**文案**

1. 尽量不用句号（短句 / 状态 / 提示 / 按钮一律无句号；仅「多个各自独立、缺了看不懂的信息单元」才用句号）。
2. 禁同义反复。
3. 亲切短句优于完整陈述。
4. 说明性文案过「存在意义」三问：① 能据此行动吗 ② 成功时是废话吗 ③ 失败时已有另一条在说吗。皆否 → 删。
5. 事实正确 ≠ 需要告诉用户。属实只是「可以写」的必要条件。
6. 与界面已有元素重复的文字删。
7. 提案至少覆盖「该删 / 该合并 / 该改措辞」三类，只改措辞等于没审。
8. 判据用于淘汰，不用于生成。

**工程**

9. 动手前先复述计划、获确认再执行；未确认不写生产文件。
10. 只提交推送自己这轮动的文件。
11. 删 key 连带清代码引用（全局搜），否则 `t()` 回退显示 key 名。
12. 只删显示层，防重入锁、状态机等逻辑别误删。
13. 事实断言必须带可复现命令与输出。
14. 回答收在用户问的那一句上。
15. 现状靠读源码推导，不靠注释 / 文档结论 / 提交说明 / 截图。
16. 提交说明用中文。
17. 代码注释引正式文档，禁 `docs/wip/` 路径。

## 前车之鉴（避开）

- **没查清来源就凭字面动刀**：误把已定稿的 `error.identifySoftEncounter` 当旧文案要改。
- **统计必须覆盖多段 key**：只认两段式的正则会漏掉多段 key（760 曾漏成 417）。
- **模块状态一律 `git log` 实算**，不凭记忆说某模块做没做。
- **死 key 判定要覆盖 `packages/` 映射表**：`formatRank()` 的映射不在前端。
- **改前查清一条 key 被哪些码共用**，否则会写出「拍到人时是假话」的方案。
- **「看看」「演示」= 出展示页、零改动**，不等于批准改代码。
- **未被采用的稿子就是被否决**，不要重新端出来当候选。
- **「恢复原版」≠ 处置**：有代价的候选必须改到能打，否则等于丢。
- **别拿关键词拼贴当写作**：从品牌语料抠「遇见 / 名字 / 图鉴」排列组合，是蹩脚造句，不是写作。
- **文案的事实底线是「不虚假宣传」，不是「覆盖所有失败分支」**；lede 效果第一，修辞放大是本职，不是撒谎。
- **把品牌锚当不能动的框**：把「路上遇见的」当成必须保留的锚，新意被锁死；还把文档里的「路边随手拍」当成限制用户想象的框。品牌句该给用户**更大的自我**，不是缩小它。
- **覆盖写文件前必须先读**：整篇 `write` 覆盖会丢掉没看到的整节——`文案撰写规范.md` 曾被覆盖掉「术语口径」「不做无意义兜底」两节与「规则越少越好」立规原则，靠 `git diff` 才捞回来。改造 = 增删改，不是重写。
- **动一条 key 前先 `git log -S "那句话"` 查来历**：`detail.softReasonFallback` 是 `605195b` 特意把 4 条分型 key 合并后留下的（那次选「只留一种」），字面看不出这层来历；不查就动，等于重开一个已决问题。
- **别把界面动作说成事物的本质**：「起个名字」不等于「旅途」本身。写「还没有旅途。起个名字，就有了。」被用户判 0 分——旅途是真的出了那趟门，起名只是创建流程里的一步。同理「换个底色」不等于「换个地方看照片」。（已入《文案撰写规范》创作类第 8 条。）
- **走查页 / 开发页的文案不落术语表**：路由挂 `/dev/*` 或只供本地走查的页面，文案直接写明文。`SettleArtPreviewPage` 的 8 条 `settle.preview.*` 曾混在用户术语表里——会被计入改造工作量，也可能被皮肤 voice 误覆盖。判据是「用户走得到吗」。（已入《文案工程规范》§一 例外。）
- **主题文本的 key 必须独立**：可文案区的 key 不得与 `common.*` 或其它共用 key 合并——voice 覆盖按 key 生效，合并即失去覆盖粒度（`common.*` 全在固定区，并进去就永远覆盖不了）。即使两套主题当下与 common 同句也不合并（如 `settle.failed` 与 `auth.failed`）。（已入《文案工程规范》§二 例外。）
