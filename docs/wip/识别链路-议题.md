## 议题 1：Gemini 日配额判定**正确**，但冷却 12h 严重过长（优先）

> **2026-09-10 更正**：初判「分钟级 429 被误判为每日耗尽，**该判断错误，已撤回**」。
> 实测 `quotaId` 明确为 `GenerateRequestsPerDayPerProjectPerModel-FreeTier`，
> 判定 `daily_exhausted` **是对的**。真正的问题是**冷却时长**与**额度浪费**，见下。

### 现状

链路：`orchestrator.identifyWithFallback()` 优先 Gemini，失败按 `health.classifyProviderError()` 分类 →
`applyError()` 打冷却 → 超 `identifyGeminiWaitMaxMs`（默认 90s）才降级 TokenHub。

[orchestrator.ts:38](/D:/Fun/BioTrace/apps/api/src/identify/orchestrator.ts) 对 `daily_exhausted` 的冷却**写死 12 小时**：

```ts
kind === "daily_exhausted" ? 12 * 60 * 60_000 : ...
```

且**不采用 Google 返回的 `retryDelay`**。

### 铁证（2026-09-10 服务器实测，非推断）

**证据 A — 配额身份与上限**（完整 `QuotaFailure.violations` 原文）：

```json
"quotaMetric": "generativelanguage.googleapis.com/generate_content_free_tier_requests",
"quotaId": "GenerateRequestsPerDayPerProjectPerModel-FreeTier",
"quotaDimensions": { "model": "gemini-3.6-flash", "location": "global" },
"quotaValue": "20"
```

→ 免费层 **每模型每日 20 次**，这是硬上限。

**证据 B — Google 以滚动窗口释放，只给秒级 `retryDelay`**（连续 12 次实测，`retryDelay` 严格递减、无反弹）：

```text
59.4s → 55.8s → 34.1s → 29.4s → 28.6s → 25.9s
     → 23.5s → 21.3s → 20.7s → 18.1s → 10.5s → 9.3s
```

最长 **59 秒**，最短 **9 秒**，全都在**分钟以内**。
（注：探测请求本身也消耗额度，导致尾部下降趋缓；即便如此，始终未出现"小时级"等待。）

→ Google 自己说：**等几十秒就能再用**。系统却封了 **12 小时 = 43200 秒**，约为 Google 建议值的 **700 倍以上**。

**证据 C — 昨天确实撞了硬顶**：
`identify_provider_daily` 2026-09-09 → gemini success 15 + fail 10 = **25 次调用 > 20 额度**。
`exhausted_at = 1788968083132`（CST 09-09 23:34:43）。

**证据 D — SDK 错误文本可直接取到上述字段**（方案可行性基础）：
`@google/generative-ai@0.24.1` 的 `dist/index.js:426-428`：

```js
if (json.error.details) {
  message += ` ${JSON.stringify(json.error.details)}`;
  errorDetails = json.error.details;
}
```

→ `quotaId` / `retryDelay` **都完整出现在 `err.message` 里**，可用正则直接匹配，无需改请求层。

### 待决

1. 冷却是否从固定 12h 改为**采用 Google 的 `retryDelay`**（`RetryInfo` 字段，现已有 `parseRetryDelayMs` 可解析），
   并保留 `identifyGeminiWaitMaxMs`（默认 90s）作为上限？
   —— 证据 B 显示 90s 上限足以覆盖绝大多数情况（最长实测 59.4s）。
2. 日配额 20 次是否够用？若不够，是否要：多 key 轮换 / 降并发 / 付费层。
   注意 `IDENTIFY_CONCURRENCY=2` 且失败重试也消耗额度。
3. **失败重试是否消耗 RPD 额度 —— 已实测确认为「不消耗」**（2026-09-10）：
   连续 6 次探测间隔 12s，得到 `retryDelay` 序列：

   ```text
   15.2s → 2.5s → 49.9s → 36.0s → 22.8s → 10.1s
   ```

   其中 probe2 仅 **2.5s**——若失败请求也计入额度，窗口只会被推得更远，不可能出现 2.5s 这种短值。
   且整体在 50s 内收敛，符合**滚动时间窗**特征：额度按时间释放，与请求次数无关。
   → 结论：**429 本身不扣额度**，昨天 8 次 503 transient 重试不构成额度浪费。
   → 但这同时意味着：即便改短冷却，也**无法突破 20 次/日的硬顶**。

## 议题 1b：日界错位（UTC 日键 vs PT 配额日）

### 现状

全系统配额按 **UTC 日**记账：`utcDayKey() = new Date().toISOString().slice(0,10)`，用于 `identify_provider_daily`、`identify_daily_usage`、平台每日额度。

而 `quotaId = GenerateRequestsPerDayPerProjectPerModel-FreeTier` 的 **PerDay 按 PT（America/Los_Angeles）午夜重置**，PT 午夜 = UTC 07:00（PDT）= CST 15:00。

### 铁证（2026-09-10 服务器上实测）

```text
date -u                      → Thu Sep 10 02:45:52 AM UTC 2026
TZ=America/Los_Angeles date  → Wed Sep  9 07:45:52 PM PDT 2026
```

即：**UTC 已翻到 09-10，PT 仍是 09-09 19:45，旧配额日还剩约 4.25 小时**。

后果：`identify_provider_daily` 在 UTC 00:00 翻页，把同一个 PT 配额日**切成两半**记账，
导致「今日用了多少 / 还剩多少」的统计**必然失真**——无法回答「离 20 次上限还有几次」。

### 待决

1. `identify_provider_daily` 的日键是否改成 PT 日键（`IDENTIFY_QUOTA_TZ` 可配，默认 `America/Los_Angeles`）？
2. 面向用户的 `IDENTIFY_DAILY_LIMIT`（`identify_daily_usage`）：用户在中国，**是否应继续按 UTC/本地日记**？
   两种日键是否要**分开**——provider 侧跟 Google 走 PT，用户侧跟用户体感走本地日？
3. 若议题 1 改为采用 `retryDelay`，则冷却终点不再依赖日界，此议题退化为**纯统计口径**问题。
