## 1. 调研结论：当前数据链路的真相

在提问题之前必须先纠正一个我此前的错误假设。**代码里的树，和原型里的树，不是同一种东西。**

### 1.1 现在的树是「我的收集树」，不是「全生物界树」

| 项 | 现状 | 证据 |
|----|------|------|
| 树的数据源 | `CollectionEntry[]`——**用户图鉴条目** | `apps/web/src/treeBuild.ts:165` `buildTreeLayer(entries, path)` |
| 树怎么来的 | 从用户已收集条目**反向聚合**出层级 | `treeBuild.ts:122` `groupByRank()` |
| 计算位置 | **纯前端、全量、每次现算** | `treeBuild.ts` 无缓存、无分页 |
| 节点的「数量」含义 | **我收集了几个**，不是全世界有几个 | `treeBuild.ts:160` `count: subset.length` |

也就是说：**树的规模 = 用户收集的多样性**。个人图鉴的现实上限是几十到几千条，不是 200 万。

**这直接推翻了我此前对问题 1 和 3 的定性**（我按"全生物界"估算了扇出与总量）。

### 1.2 分类阶元只有 7 级，且次级阶元被主动丢弃

回答「项目里会对亚门、亚纲这些做记录吗」：**不会，而且是主动折叠掉的。**

| 项 | 现状 | 证据 |
|----|------|------|
| 阶元集合 | 硬编码 7 级，无中间阶元 | `apps/api/src/identify/types.ts:1-11` `TAXONOMY_RANKS` |
| 数据库存法 | **没有阶元列**，整条链塞进一个 JSON 文本字段 | `apps/api/src/db/schema.ts:86` `taxonomyJson: text(...)` |
| 树结构 | **无 `parent_id`**。每条观察各带一份自己的完整链快照（冗余） | `types.ts:18` `Record<TaxonomyRank, TaxonomyName>` |
| rank 枚举 | DB 层是裸 TEXT，无约束 | `schema.ts` `finestReliableRank: text(...)` |
| 次级阶元 | **主动折叠**：亚种→种，亚科/总科/族→科 | `apps/api/src/settle/taxon.ts:86-109` `RANK_ALIASES`；`apps/api/src/rarity/gbif.ts:18-45` `rankParam` |
| AI 输出 | prompt 只要 7 键；解析时非 7 键**直接丢弃** | `identify/prompt.ts:62-65`；`types.ts:69-89` `normalizeTaxonomy()` |
| 预计算后代计数 | **没有**。全部 DDL 无任何 count 列 | `apps/api/src/db/index.ts:31-126` |
| 前端镜像 | 同样硬编码 7 级 | `apps/web/src/api.ts:3-12`、`treeBuild.ts:4-13`、`apps/api/src/volumes/load.ts:8-10` |

**结论：识别流程→落库→前端，全链路都没有亚门/亚纲的位置。** 你的判断成立——**没有数据，渲染层支持它没有意义。这条可以直接关掉，不必再讨论。**

（`packages/messages` 里出现过「亚纲」字样，是文案里的偶发词，不是阶元定义。）

## 2. 根本岔路口（**待你拍板**）

原型（`prototypes/clear-tree/`）用的 mock 数据是 **14 万种、六界齐全的完整分类树**。这隐含假设了"全景树"。但线上代码是"收集树"。两者对不上。

而你对这个界面反复强调的核心体验是：

> 「核心的体验就是感觉到这颗树的雄伟庞大，用户在生物界中的遨游」

**这跟「纯收集树」是有张力的**：新用户收集 3 个物种，树就是 3 根枝，无论怎么渲染都不可能雄伟。这个矛盾不是美术能补的。

### 方案 A：纯收集树（= 现在的实现）

| | |
|---|---|
| 树包含 | 只有已收集的物种及其上溯链路 |
| 雄伟感 | 靠长期积累。**冷启动必然是空的** |
| 扇出 | 天然很小（问题 1 基本消失） |
| 加载 | 全量前端算即可（问题 3 基本消失） |
| 数据改动 | **零**。现有结构够用 |
| 代价 | 与「遨游生物界」的叙事不符；新用户看不到"庞大" |

### 方案 B：全景骨架 + 点亮

| | |
|---|---|
| 树包含 | 完整（或裁剪过的）分类骨架；已收集的**点亮**，未收集的**暗淡** |
| 雄伟感 | **第一次打开就有**；且天然产生"待探索"的驱动力 |
| 扇出 | **变成真问题**（见 §3.1） |
| 加载 | **变成真问题**（见 §3.3） |
| 数据改动 | 需要引入**真正的分类树表**（`parent_id` + 预计算计数） + 一份骨架数据源 |
| 代价 | 工程量显著变大；需要选定并导入外部分类数据 |

### 方案 C：分层折中

总览层用骨架（到科级，约 1.5 万节点，足够"庞大"），科以下只显示已收集的。既有冷启动的雄伟感，又避免"点亮率 0.01%"的挫败感和全量加载。

> **待决 ①**：选 A / B / C？
> **→ 已拍板：C（分层折中），骨架切在「目」。见 §4.1。**
> （下文 §3 的分析仍有效，但结论以 §4 为准。）

## 3. 三个问题的重新定性

### 3.1 大扇出

**原始描述**：真实数据里菊科下约 1900 属，一屏放不下。

**重新定性**：

- 若选 **A**：**基本不是问题**。用户图鉴里"蔷薇科"下大概率只有个位数属。
- 若选 **B/C**：**是真问题，且渲染层无解**。1900 个子节点不可能一屏展示，这不是布局算法能救的。

可选处理方向（**未验证，仅列出供讨论**）：

| 方向 | 说明 | 风险 |
|------|------|------|
| 按体量聚类 | 前 N 大的单独成枝，其余归并成若干「其他 N 属」的枝，可继续下钻 | 保住了树的隐喻；但"其他"的分组规则要讲得通 |
| 分页 / 翻页 | 一屏 12 个，可翻 | **会把树退化成列表**，与你的硬要求冲突 |
| 首字母索引 | 按拉丁名首字母分组成枝 | 分组无生物学含义，像目录 |
| 搜索优先 | 大扇出节点默认引导搜索 | 是逃避，不是解决 |
| 只显示已点亮 + 计数 | 大扇出节点下只展开已收集的，其余用一个"还有 1888 属未探索"的暗示 | 与 C 天然契合 |

> **待决 ②**：大扇出怎么处理？
> **→ 仍未决。已按「页面容量 × 已收集数」细分为 4 种情况，见 §4.4。**

### 3.2 深度不齐

**原始描述**：真实分类有亚门/亚纲等中间阶元，我按严格 7 层做。

**重新定性（09-04）——这不是缺陷，是分类树本来的样子。**

林奈阶元是标签，不是格子。命名法规不要求每条谱系都有齐整的「界→门→纲→目→科→属→种」。同一父节点下可以同时挂着不同阶元的孩子（门下既有纲又有目）；一条链也可以跳过某一级（没有纲，目直接挂在门下）。GBIF Backbone / Catalogue of Life 都这样存。骨架里大约 6% 的节点相对父级跳了至少一阶，有子级的父节点里大约 4% 底下混着两种阶元，多界都有，不是某个类群的特例。

业界默认：**按父子关系挂，缺的级不造。** Catalogue of Life 浏览树可选插一个虚拟「未指定」夹（浏览辅助，不是真分类）。往每条谱系填假阶元（Taxallnomy 一类）是给表格统计用的权宜名，不能当成真节点——和「亚门/亚纲不做」同一条。

所以问题不是「深度不齐要修齐」，而是实现曾按齐整 7 层来想：

| 曾做错的假设 | 正确约束 |
|---|---|
| 子级阶元 = 自己 + 1 | 文案按子级**实际**阶元分组（概要卡已改，不再把混阶元说成「全是纲」） |
| 所有叶子都在种这一层 | 识别住在哪一级就住哪一级。3D 点亮分类，照片在「查看收集」（③a 已结案） |
| 枝长/段数/点亮按「第几层格子」和阶元混用 | **点亮和名字跟真实阶元**（纲不灰、目才灰；标签写「目」就是目）。**枝按父子边长**，不要为了对齐格子去插假节点 |
| 缺的级补上亚门/亚纲/假纲 | **不做**（§1.2 / §3.2a） |

**(a) 中间阶元（亚门/亚纲）→ 结案，不做。**
理由见 §1.2：全链路无数据，且被主动折叠。

**(b) 识别叶子不住种级、未归位 → 已从本条拆出。**
不是分类树深度不齐。识别只到科时条目住在科上，见 §4.5a（已结案）。没界的不进图鉴，见 §4.5b（已结案）。

> **不是待修的几何工单。** 留下的只是约束：不要按齐整 7 层写死文案或造假节点。接收集数据后若再发现写死齐层的代码，按上表改，不要改成「相对深度 = 新阶元」。

### 3.3 总量与加载

**原始描述**：200 万物种不可能全量常驻。

**重新定性**：

- 若选 **A**：**不是问题**。现在全量前端算，几千条以内没压力。
- 若选 **B/C**：是问题，但是**标准的按需加载问题**，不难，只是工程量。原型的展开缓冲本来就是按需重建的，渲染层已经兼容。

**但这里有一个独立于 A/B/C 的真问题：节点的「数量」含义。**

现在 `count` 是 `subset.length`，即**我收集了几个**（`treeBuild.ts:160`）。

原型里显示的是 `cnt`，语义上当作了**这一支下面总共有多少种**——用来决定枝的粗细与长度（"含种越多的支越长越壮"）。这两个是不同的东西：

| 语义 | 用途 | 现在有吗 |
|------|------|----------|
| 我收集了几个 | 成就感、进度 | 有（前端现算） |
| 全世界有几个 | 决定枝的体量，撑起"雄伟" | **没有** |

若选 B/C，「全世界有几个」必须**后端预计算成字段**，前端不可能算。

> **待决 ④**：枝的粗细/长度由哪个数决定？
> **→ 已拍板：都不用。用 hash 扰动，同阶元内视为平等。见 §4.3。**

## 4. 已拍板的决策（2026-09-02 ~ 09-03 讨论）

### 4.1 ① 树的形态 = **分层折中（方案 C）** ✅ 已拍板

```
界 → 门 → 纲 → 目     ← 静态全景骨架，人人相同，一次性内置
科 → 属 → 种          ← 只长已收集的，配「还有 N 属未探索」
```

**骨架切在「目」的理由**（这是整个方案的支点）：

| 切在 | 节点数 | 冷启动雄伟感 | 点亮率观感 | 大扇出 |
|---|---|---|---|---|
| 纲 | ~800 | 够 | 10/800 尚可 | 无 |
| **目** | **~3500** | **很够** | **15/3500 = 探索进度** | **无** |
| 科 | ~20000 | 过剩 | 30/20000 = 挫败 | 开始出现 |
| 种 | ~2000000 | — | 0.001% = 劝退 | 灾难 |

**关键收益：目级以上的扇出天然都不大**（界→门 ≤40，门→纲 ≈30，纲→目 ≈30）。
所以 **§4.4 的大扇出问题在全景骨架部分根本不会出现** —— 它只出现在科→属。

**成本极低（调研后才看清）**：
- 骨架数据从 GBIF backbone 导一次，~3500 行静态 JSON，gzip 后 ~50KB，**内置不查库**
- **不需要动数据库、不需要新表、不需要 `parent_id` 改造**
- 现有 `taxonomy_json` 足够定位「我的条目挂在哪个目下」

### 4.2 界的划分 = GBIF 8 界 + 「高度即可及性」三段式 ✅ 已拍板

数据源必须与 GBIF 一致（否则对不上）。但 8 界的**可拍摄性**差异极大，
所以按可及性分三段，形成一条垂直梯度：

| 位置 | 类群 | 表现 | 依据 |
|------|------|------|------|
| **树冠主枝** | 动物、植物、真菌 | 鲜艳，360° 均分，撑起整个树冠 | 真核 + 手机可拍 |
| **树冠矮枝** | 色藻（褐藻/海带）、原生动物（黏菌） | 主干 0.70 高处分出的短小侧枝，轻度淡化 | 真核 ✓ 在地上；少数宏观可拍 |
| **地下根系** | 细菌（蓝藻水华）、古菌（粉红盐湖）、病毒 | 去饱和 + 随深度渐隐，水平广铺 | 原核 = 真核的来源；隐微不可见 |

**「高度即可及性」**：越往上越容易拍到，越往下越隐微，地下几乎不可见。
既符合生物学（原核在根，真核在地上），也符合直觉。

> **09-04 修正**：原方案把色藻/原生动物做成「主干 1/3 高的近地矮丛」。落地后发现
> 两个毛病：① 语义不对 —— 它们不是「介于地上地下之间」，就是不起眼的真核生物；
> ② 视觉上贴在主干腰上像两个瘤子，且被铺宽的根系抢戏。改为树冠里的矮枝，
> 见 §4.7。**色彩上仍轻度淡化（`zone: basal` 不变），只改几何。**

**病毒界：保留，放根系最深处，恒灰，点进去提示「不可收录」。**

> 讨论中我曾主张「病毒不在生命之树上（非细胞、无共同祖先），应做成不连枝的漂浮微粒」。
> **这个论证是错的**：林奈分类树本身不表达祖先关系，我自己前面刚说过这一点，
> 转头又拿祖先关系去论证 —— 框架混用。GBIF backbone 把 Viruses 列为一界，
> 在分类树语境下它就该在树上。

### 4.3 ④ 枝的体量 = **hash 扰动，不用任何真实数量** ✅ 已拍板

- 形态：`hash(节点ID)` 决定长度/粗细的 ±20% 扰动。**恒定**（同节点永远同值）、
  人人一致、零数据成本。只为打散机械对称
- **同一阶元内视为平等**，不按数量分大小
- 界级（只有 3 支）**完全不加扰动** —— 只有三支时任何差异都会读成「一高一矮」的畸形
- **总览树冠也不跟真实节点数走**（2026-09-03 补记）：骨架里动物末端远多于植物，
  若按节点数长枝，动物会独大。做法是视觉作弊——同阶分叉把长度分薄、三界装饰叶拉到同一预算。
  点进去仍是完整分类，只是总览「大概画」成三蓬差不多大的树冠。
  不是「把动物画小」这种特例。

**废弃的方案：用 GBIF「带照片的人类观察记录数」定体量。** 两个理由：
1. 一屏只看一级，在界层面无从对比属级的数量差 —— 体量差异传达不了信息
2. 该数字受**采集偏差**支配（鸟类记录暴涨是 eBird 社区效应，不是生物事实），
   它展示的是「人类观察偏好」而非生物多样性，不比 hash 更「真」，却贵得多

**雄伟感来自 3D 渲染的枝条与海量叶子，不需要真实数据背书。**

### 4.4 ② 大扇出 —— 仍未决，但已细分为 4 种情况

真实数据里菊科下约 1900 属，一屏放不下。分层折中把它限定在科→属，但仍需方案。
按「页面容量」与「已收集数」交叉，分 4 种情况，**方案可能各不相同**：

| # | 情况 | 说明 | 处理方向（未定） |
|---|------|------|------------------|
| 1 | 节点数刚好（~10 个） | 最理想 | 直接全展开 |
| 2 | 总数超出，**已收集不超出** | 骨架 1900 属，你收集了 5 个 | 只展开已收集 + 「还有 1895 属未探索」。早期最常见 |
| 3 | 总数超出，**已收集也超出** | 你收集了 50 个属 | **真正需要折叠**。这是最难的一种 |
| 4 | **已收集不足（0~1）**，总数超出 | 几乎全未探索 | 只显示列表会近乎空白、很挫败。应反过来表达**规模感** |

**情况 4 的洞察**：不该显示"列表"，该显示"这片林子有多大" ——
用密集但不可读的淡色枝丛 + 「1900 属待探索」，把空白转成敬畏与探索欲。

**情况 3 的一个候选（待评估）**：**分批「生长」**而非分页 ——
一次显示 12 个，其余聚成枝端一个饱满的「芽/苞」，点芽绽开、继续长出下一批。
保持树的隐喻，不退化成列表。

> 待办：去交互/艺术类作品找折叠的表现形式灵感（用户建议）。
>
> **2026-09-03：** 这是大问题，先遗留。不满意「骨架切在目，早期就不会碰上」当成方案 ——
> 切在目只是把扇出推迟到科→属，不是把问题做掉。

### 4.5 ③ 非种级叶子 + 未归位

**(a) 非种级叶子 —— 已结案 09-03**

识别只到科时，这条收集「住」在科上。3D 树点亮这个科；照片在概要卡的「查看收集」里，点进去看。
**不在 3D 扇形上再长一片叶。** 树负责「这个分类在哪、亮不亮」，列表负责「拍到了哪张照片」。

**(b) 未归位 —— 已结案 09-03：树上不要入口**

连界都认不出的照片，不在树上做「未归位」角落。不是每张照片都要进树。
识图门槛 **已做 09-04**：`evaluateEligibility` 在 collectible 时要求 `taxonomy.kingdom.name_la`，否则 `identify_no_kingdom`，不进图鉴。旧条目不回刷。

### 4.6 点亮态 —— 已拍板 09-03（此前口说未记）

- **界 / 门 / 纲**：不因收集变灰。即使从未收集，也显示预备好的名字（骨架中文表）。
- **目 / 科 / 属 / 种**：没收集的灰，收集过的饱和。

总览时主干和主枝仍是满色，灰的是目级末梢 —— 冷启动的雄伟感在界门纲，足迹在目以下。

纲的中文覆盖目前只有 28%，预备名字不全是另一件事（补表），不是灰置。

「门纲挤成圆点」是标签放不下，和灰置不是同一件事。
**2026-09-03：** 圆点取舍整套机制用户不喜欢（门多时大量圆点、名字忽隐忽现）。
根因：碰撞就降成圆点；展开时镜头还在微晃，每帧重算谁留下，于是闪。当大问题，先不另做一套。

### 4.7 树冠布局 = 写死三档高度 + 动物/植物各拆两支 ✅ 已拍板 09-04

代码：`apps/web/src/tree/TreeScene.ts` 的 `CANOPY` / `TIER_LEN` / `growForked()`。

**① 高度写死三档，不随数据浮动。**

| 档 | 类群 | 枝长（主干高的倍数） | 起点 |
|----|------|--------------------|------|
| 高 | 动物、植物 | 0.72 | 主干顶 |
| 中 | 真菌 | 0.62 | 主干顶 |
| 矮 | 色藻、原生动物 | 0.20 | 主干 0.70 高 |

档内再加 `hash(节点ID)` 的 ±8% 扰动，避免同档几根一模一样长（§4.3 的延续）。
**关键是「不随子级数量浮动」** —— 原来按节点数定长短，数据一变形态就跟着乱。

**② 动物、植物各拆成两支主枝，且两支相邻。**

34 个门全挂一根枝上会粗得像根柱子，没有大枝杈的体量感。做法是：
界画成「一短柄（0.30L）+ 两根次主枝（0.76L）」，门平分到两支上。

- **纯几何，数据结构不变。** 次主枝没有对应节点，顶点写在本界的 `[vs, ve)` 区间内，
  `collapse` / `fanReset` / 焦点隐藏都会连带处理，不需要为它加任何分支逻辑
- **两支必须相邻**（`CANOPY` 表的书写顺序保证），同色成簇才读得出「这是一个界」

**③ 枝位是全树共用的角度刻度，拆枝的每一支各占一位。**

动物 2 + 植物 2 + 真菌 1 = 5 个枝位，圆周上 72° 等分。矮枝插在枝位的空隙里
（枝位在 `(k+0.5)·gap`，空隙就在 `k·gap`），才不会被大枝正面盖住。

> **踩坑记录**：第一版按「界」分角度、两支挤在同一枝位附近张开，结果 5 个枝位
> 只用了 3 个方向，树整个偏向一侧。必须按**枝位**而不是按**界**分配角度。

**④ 连带删除 `grow()` 里 `isBasal` 的几何特例。**

`isBasal` 原本让子级 `spreadK ×1.45` 且**全部强制外沿满长**，那是为「贴地矮丛」写的。
色藻/原生动物进树冠后这套仍在生效，把它们撑成了两个蒲公英球。删掉后
basal 的几何与 crown 完全一致，只保留颜色上的轻度淡化。

## 5. 渲染实现的经验值（防止重复踩坑）


外观调整基本只需改参数，但以下几个参数**极其敏感**，改动前先读这里：

| 参数 | 教训 |
|------|------|
| `decay`（枝长衰减） | 这是 6 层复合的**指数**。0.68 → 0.755 会让末端枝长翻倍，**单个界就能撑爆整个画面**。0.70~0.74 是平衡区 |
| 枝的宽长比 | 应在 **0.03~0.06**，真实树枝就在这个范围。到 0.14 就是一根棒子。改长度后必须同比改宽度 |
| `photo`（趋光偏置） | 树冠必须**由正转负**（内层上举、外缘下垂），冠才是圆的。全程为正 → 所有枝互相平行 → 冠顶压平、下半空掉 = 「沙漠合欢」 |
| `spread`（分叉角） | 只有 3 根主枝要填满 360°（不是 6 根），每支张角必须更大 |
| 子级绕枝方位 | **必须均匀分布 + 小扰动**。纯黄金角螺旋只在数量多时才均匀；每节点只有 3~5 个子级时螺旋会把它们堆在一侧，逐层放大后整棵树偏心 |
| 子级分叉位置 | **必须沿父枝全长错落分出**。若都从父枝末端一点爆开，每个节点会长成独立的球，整棵树成了「三叉戟挂三个球」，球之间必然空 |
| 地面散点半径 | 铺得比树冠还宽会变满屏噪点，且俯视下远处地面会投影到画面上方、把根系淹掉。噪点要靠**降低着色**压制，不是缩小面积 |
| 包围盒 | **必须统计叶点**，不能只算枝顶点 —— 叶簇长在枝端之外，只算枝会低估树的范围，取景必然溢出 |
| 根系「广」 | 加长根枝会又宽又深。正确做法是**把方向的竖直分量压扁**（×0.30），长度全部转化为水平延展 |
| 叶点形状 | 实心圆 sprite 放大后就是一堆小球。解法：fragment 里**按每点 seed 旋转 UV**画细长叶片，并按屏幕尺寸在「柔边圆点（远）↔ 叶片（近）」之间过渡。（点精灵本身无法旋转，但 UV 可以旋转 —— 我曾误判为不可行） |
| 展开层段数 | 大树缓冲给深层枝只分 2~4 段（总览时只占几像素），展开后放大到半屏就是折线。需要**单独一套 10 段的展开缓冲**（~600 根枝，4MB），不能全局提高段数（要 59MB） |
| 深入态的雾 | 会叠加在叶点自身的提亮上，把颜色洗成灰白。`uFogK` 展开态要压到 0.3 左右 |
| 隐微感 | 要靠**去饱和**，不能靠提亮 —— 提亮会把根系洗成白色，在浅底上彻底消失 |

**主干必须直立**：`axialOut` 里 `A[0] || fallback` 的写法，在主干（起点 `[0,0,0]`）
上会因 `0` 是 falsy 而走 fallback 分支，把主干强行推向 +X，整个树冠随之偏心。
