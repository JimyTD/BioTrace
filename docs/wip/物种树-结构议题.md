## 1. 调研结论

### 1.1 开这篇时线上是收集树；现在已经不是

2026-09-02 写这一节时，界面上的树是从用户图鉴反向聚合的（当时的 `treeBuild.ts` / `buildTreeLayer`）。原型却是 14 万种全景 mock。两边对不上，才有 §2 的 A/B/C。

**09-03 拍板分层折中之后，现行实现是：**

| 项 | 现状 | 证据 |
|----|------|------|
| 骨架 | GBIF 界→目，内置不查库（2026-09-08 起 3803 节点、八界全导；细菌/古菌/病毒根系真数据已入库） | `apps/web/src/data/backbone.json`、`tree/treeModel.ts` `buildSpeciesTree` |
| 收集 | 科→属→种只长已收集的 | `treeModel.ts` `attachEntry` |
| 渲染 | 整页 WebGL，不是文件夹宫格 | `tree/TreeScene.ts`、`SpeciesTree3D.tsx` |
| 节点上的「数量」 | 这一支下**我收集了几项**（`got`），不是全世界有几种 | `treeModel.ts` `rollup` |

树的规模不再等于收集条数。冷启动也能看到全景骨架。`treeBuild.ts` 里的建树已经删了，只留下 `isPlaced` / `homeRank` / `countTreeKingdoms`。

### 1.2 分类阶元只有 7 级，且次级阶元被主动丢弃

回答「项目里会对亚门、亚纲这些做记录吗」：**不会，而且是主动折叠掉的。**

| 项 | 现状 | 证据 |
|----|------|------|
| 阶元集合 | 硬编码 7 级，无中间阶元 | `apps/api/src/identify/types.ts:1-11` `TAXONOMY_RANKS` |
| 数据库存法 | **没有阶元列**，整条链塞进一个 JSON 文本字段 | `apps/api/src/db/schema.ts:86` `taxonomyJson: text(...)` |
| 树结构 | **无 `parent_id`**。每条观察各带一份自己的完整链快照（冗余） | `types.ts:18` `Record<TaxonomyRank, TaxonomyName>` |
| rank 枚举 | DB 层是裸 TEXT，无约束 | `schema.ts` `finestReliableRank: text(...)` |
| 次级阶元 | **主动折叠**：亚种→种，亚科/总科/族→科 | `apps/api/src/settle/taxon.ts:86-109` `RANK_ALIASES`；`apps/api/src/rarity/gbif.ts:18-45` `rankParam` |
| AI 输出 | prompt 只要 7 键；解析时非 7 键**直接丢弃** | `identify/prompt.ts:62-65`；`types.ts:69-89` `normalizeTaxonomy()` |
| 预计算后代计数 | **没有**。全部 DDL 无任何 count 列 | `apps/api/src/db/index.ts:31-126` |
| 前端镜像 | 同样硬编码 7 级 | `apps/web/src/api.ts`、`tree/treeModel.ts` `RANKS`、`apps/api/src/volumes/load.ts` |

**结论：识别流程→落库→前端，全链路都没有亚门/亚纲的位置。** 你的判断成立——**没有数据，渲染层支持它没有意义。这条可以直接关掉，不必再讨论。**

（`packages/messages` 里出现过「亚纲」字样，是文案里的偶发词，不是阶元定义。）

## 2. 根本岔路口（已拍板：分层折中）

开这篇时：原型是全景树，线上是收集树，两者对不上。下面三套是当时的选项。**已选 C**，骨架切在「目」，见 §4.1。

而你对这个界面反复强调的核心体验是：

> 「核心的体验就是感觉到这颗树的雄伟庞大，用户在生物界中的遨游」

**这跟「纯收集树」是有张力的**：新用户收集 3 个物种，树就是 3 根枝，无论怎么渲染都不可能雄伟。这个矛盾不是美术能补的。

### 方案 A：纯收集树

| | |
|---|---|
| 树包含 | 只有已收集的物种及其上溯链路 |
| 雄伟感 | 靠长期积累。**冷启动必然是空的** |
| 扇出 | 天然很小（问题 1 基本消失） |
| 加载 | 全量前端算即可（问题 3 基本消失） |
| 数据改动 | **零**。现有结构够用 |
| 代价 | 与「遨游生物界」的叙事不符；新用户看不到"庞大" |

### 方案 B：全景骨架 + 点亮

| | |
|---|---|
| 树包含 | 完整（或裁剪过的）分类骨架；已收集的**点亮**，未收集的**暗淡** |
| 雄伟感 | **第一次打开就有**；且天然产生"待探索"的驱动力 |
| 扇出 | **变成真问题**（见 §3.1） |
| 加载 | **变成真问题**（见 §3.3） |
| 数据改动 | 需要引入**真正的分类树表**（`parent_id` + 预计算计数） + 一份骨架数据源 |
| 代价 | 工程量显著变大；需要选定并导入外部分类数据 |

### 方案 C：分层折中

总览层用骨架（到科级，约 1.5 万节点，足够"庞大"），科以下只显示已收集的。既有冷启动的雄伟感，又避免"点亮率 0.01%"的挫败感和全量加载。

> **已拍板 ①**：C（分层折中），骨架切在「目」。见 §4.1。
> （下文 §3 的分析仍有效，但结论以 §4 为准。）

## 3. 三个问题的重新定性

### 3.1 大扇出

**原始描述**：真实数据里菊科下约 1900 属，一屏放不下。

**重新定性**：

- 若选 **A**：**基本不是问题**。用户图鉴里"蔷薇科"下大概率只有个位数属。
- 若选 **B/C**：**是真问题，且渲染层无解**。1900 个子节点不可能一屏展示，这不是布局算法能救的。

可选处理方向（**未验证，仅列出供讨论**）：

| 方向 | 说明 | 风险 |
|------|------|------|
| 按体量聚类 | 前 N 大的单独成枝，其余归并成若干「其他 N 属」的枝，可继续下钻 | 保住了树的隐喻；但"其他"的分组规则要讲得通 |
| 分页 / 翻页 | 一屏 12 个，可翻 | **会把树退化成列表**，与你的硬要求冲突 |
| 首字母索引 | 按拉丁名首字母分组成枝 | 分组无生物学含义，像目录 |
| 搜索优先 | 大扇出节点默认引导搜索 | 是逃避，不是解决 |
| 只显示已点亮 + 计数 | 大扇出节点下只展开已收集的，其余用一个"还有 1888 属未探索"的暗示 | 与 C 天然契合 |

> **待决 ②**：大扇出怎么处理？
> **→ 仍未决。已按「页面容量 × 已收集数」细分为 4 种情况，见 §4.4。**

### 3.2 深度不齐

**原始描述**：真实分类有亚门/亚纲等中间阶元，我按严格 7 层做。

**重新定性（09-04）——这不是缺陷，是分类树本来的样子。**

林奈阶元是标签，不是格子。命名法规不要求每条谱系都有齐整的「界→门→纲→目→科→属→种」。同一父节点下可以同时挂着不同阶元的孩子（门下既有纲又有目）；一条链也可以跳过某一级（没有纲，目直接挂在门下）。GBIF Backbone / Catalogue of Life 都这样存。骨架里大约 6% 的节点相对父级跳了至少一阶，有子级的父节点里大约 4% 底下混着两种阶元，多界都有，不是某个类群的特例。

业界默认：**按父子关系挂，缺的级不造。** Catalogue of Life 浏览树可选插一个虚拟「未指定」夹（浏览辅助，不是真分类）。往每条谱系填假阶元（Taxallnomy 一类）是给表格统计用的权宜名，不能当成真节点——和「亚门/亚纲不做」同一条。

所以问题不是「深度不齐要修齐」，而是实现曾按齐整 7 层来想：

| 曾做错的假设 | 正确约束 |
|---|---|
| 子级阶元 = 自己 + 1 | 文案按子级**实际**阶元分组（概要卡已改，不再把混阶元说成「全是纲」） |
| 所有叶子都在种这一层 | 识别住在哪一级就住哪一级。3D 点亮分类，照片在「查看收集」（③a 已结案） |
| 枝长/段数/点亮按「第几层格子」和阶元混用 | **点亮和名字跟真实阶元**（纲不灰、目才灰；标签写「目」就是目）。**枝按父子边长**，不要为了对齐格子去插假节点 |
| 缺的级补上亚门/亚纲/假纲 | **不做**（§1.2 / §3.2a） |

**(a) 中间阶元（亚门/亚纲）→ 结案，不做。**
理由见 §1.2：全链路无数据，且被主动折叠。

**(b) 识别叶子不住种级、未归位 → 已从本条拆出。**
不是分类树深度不齐。识别只到科时条目住在科上，见 §4.5a（已结案）。没界的不进图鉴，见 §4.5b（已结案）。

> **不是待修的几何工单。** 留下的只是约束：不要按齐整 7 层写死文案或造假节点。接收集数据后若再发现写死齐层的代码，按上表改，不要改成「相对深度 = 新阶元」。

### 3.3 总量与加载

**原始描述**：200 万物种不可能全量常驻。

**重新定性**：

- 若选 **A**：**不是问题**。现在全量前端算，几千条以内没压力。
- 若选 **B/C**：是问题，但是**标准的按需加载问题**，不难，只是工程量。原型的展开缓冲本来就是按需重建的，渲染层已经兼容。

**但这里有一个独立于 A/B/C 的真问题：节点的「数量」含义。**

现在节点上的 `got` 是这一支下**我收集了几项**（`treeModel.ts` `rollup`），不是全世界有几种。

原型里显示的是 `cnt`，语义上当作了**这一支下面总共有多少种**——用来决定枝的粗细与长度（"含种越多的支越长越壮"）。这两个是不同的东西：

| 语义 | 用途 | 现在有吗 |
|------|------|----------|
| 我收集了几个 | 成就感、进度 | 有（前端现算） |
| 全世界有几个 | 决定枝的体量，撑起"雄伟" | **没有** |

若选 B/C，「全世界有几个」必须**后端预计算成字段**，前端不可能算。

> **待决 ④**：枝的粗细/长度由哪个数决定？
> **→ 已拍板：都不用。用 hash 扰动，同阶元内视为平等。见 §4.3。**

## 4. 已拍板的决策（2026-09-02 ~ 09-03 讨论）

### 4.1 ① 树的形态 = **分层折中（方案 C）** ✅ 已拍板

```
界 → 门 → 纲 → 目     ← 静态全景骨架，人人相同，一次性内置
科 → 属 → 种          ← 只长已收集的。不显示「还有 N 属未探索」
```

**骨架切在「目」的理由**（这是整个方案的支点）：

| 切在 | 节点数 | 冷启动雄伟感 | 点亮率观感 | 大扇出 |
|---|---|---|---|---|
| 纲 | ~800 | 够 | 10/800 尚可 | 无 |
| **目** | **~3800**（现行入库，2026-09-08 起含根系三界） | **很够** | 探索进度 | **骨架上仍有**（见下） |
| 科 | ~20000 | 过剩 | 30/20000 = 挫败 | 开始出现 |
| 种 | ~2000000 | — | 0.001% = 劝退 | 灾难 |

切在目只挡住了菊科那种「一科下 1900 属」。**骨架自己仍有大扇出**：最大是脊索动物门 62 个子级（纲和目混挂），扇出 >40 的有 7 个。所以 §4.4 在点进门/纲时就会碰上，不能拿「切在目」当结案。

**成本极低（调研后才看清）**：
- 骨架数据从 GBIF backbone 导一次，现行 `backbone.json` **3803** 节点（八界全导；2026-09-08 根系三界真数据入库，旧版 1914 节点只含树冠+近地），gzip 后约 21KB，**内置不查库**
- **不需要动数据库、不需要新表、不需要 `parent_id` 改造**
- 现有 `taxonomy_json` 足够定位「我的条目挂在哪个目下」

### 4.2 界的划分 = GBIF 8 界 + 「高度即可及性」三段式 ✅ 已拍板

数据源必须与 GBIF 一致（否则对不上）。但 8 界的**可拍摄性**差异极大，
所以按可及性分三段，形成一条垂直梯度：

| 位置 | 类群 | 表现 | 依据 |
|------|------|------|------|
| **树冠主枝** | 动物、植物、真菌 | 鲜艳，360° 均分，撑起整个树冠 | 真核 + 手机可拍 |
| **树冠矮枝** | 色藻（褐藻/海带）、原生动物（黏菌） | 主干 0.70 高处分出的短小侧枝，轻度淡化 | 真核 ✓ 在地上；少数宏观可拍 |
| **地下根系** | 细菌（蓝藻水华）、古菌（粉红盐湖）、病毒 | 去饱和 + 随深度渐隐，水平广铺 | 原核 = 真核的来源；隐微不可见 |

**「高度即可及性」**：越往上越容易拍到，越往下越隐微，地下几乎不可见。
既符合生物学（原核在根，真核在地上），也符合直觉。

> **09-04 修正**：原方案把色藻/原生动物做成「主干 1/3 高的近地矮丛」。落地后发现
> 两个毛病：① 语义不对 —— 它们不是「介于地上地下之间」，就是不起眼的真核生物；
> ② 视觉上贴在主干腰上像两个瘤子，且被铺宽的根系抢戏。改为树冠里的矮枝，
> 见 §4.7。**色彩上仍轻度淡化（`zone: basal` 不变），只改几何。**

**病毒界：保留，放根系最深处，恒灰，点进去提示「不可收录」。**

> 讨论中我曾主张「病毒不在生命之树上（非细胞、无共同祖先），应做成不连枝的漂浮微粒」。
> **这个论证是错的**：林奈分类树本身不表达祖先关系，我自己前面刚说过这一点，
> 转头又拿祖先关系去论证 —— 框架混用。GBIF backbone 把 Viruses 列为一界，
> 在分类树语境下它就该在树上。

### 4.3 ④ 枝的体量 = **hash 扰动，不用任何真实数量** ✅ 已拍板

- 形态：`hash(节点ID)` 决定长度/粗细的 ±20% 扰动。**恒定**（同节点永远同值）、
  人人一致、零数据成本。只为打散机械对称
- **同一阶元内视为平等**，不按数量分大小
- 界级（只有 3 支）**完全不加扰动** —— 只有三支时任何差异都会读成「一高一矮」的畸形
- **总览树冠也不跟真实节点数走**（2026-09-03 补记）：骨架里动物末端远多于植物，
  若按节点数长枝，动物会独大。做法是视觉作弊——同阶分叉把长度分薄、三界装饰叶拉到同一预算。
  点进去仍是完整分类，只是总览「大概画」成三蓬差不多大的树冠。
  不是「把动物画小」这种特例。

**废弃的方案：用 GBIF「带照片的人类观察记录数」定体量。** 两个理由：
1. 一屏只看一级，在界层面无从对比属级的数量差 —— 体量差异传达不了信息
2. 该数字受**采集偏差**支配（鸟类记录暴涨是 eBird 社区效应，不是生物事实），
   它展示的是「人类观察偏好」而非生物多样性，不比 hash 更「真」，却贵得多

**雄伟感来自 3D 渲染的枝条与海量叶子，不需要真实数据背书。**

### 4.4 ② 大扇出 —— 已拍板 09-08

真实数据里菊科下约 1900 属，一屏放不下。分层折中把它限定在科→属，但仍需方案。
按「页面容量」与「已收集数」交叉，分 4 种情况，**方案可能各不相同**：

| # | 情况 | 说明 | 处理方向（未定） |
|---|------|------|------------------|
| 1 | 节点数刚好（~10 个） | 最理想 | 直接全展开 |
| 2 | 总数超出，**已收集不超出** | 骨架 1900 属，你收集了 5 个 | 只展开已收集 + 「还有 1895 属未探索」。早期最常见 |
| 3 | 总数超出，**已收集也超出** | 你收集了 50 个属 | **真正需要折叠**。这是最难的一种 |
| 4 | **已收集不足（0~1）**，总数超出 | 几乎全未探索 | 只显示列表会近乎空白、很挫败。应反过来表达**规模感** |

**情况 4 的洞察**：不该显示"列表"，该显示"这片林子有多大" ——
用密集但不可读的淡色枝丛 + 「1900 属待探索」，把空白转成敬畏与探索欲。

**情况 3 的一个候选（待评估）**：**分批「生长」**而非分页 ——
一次显示 12 个，其余聚成枝端一个饱满的「芽/苞」，点芽绽开、继续长出下一批。
保持树的隐喻，不退化成列表。

#### 落地现状与实测（2026-09-07）

总览已定稿（见 [`物种树-拍板铁律.md`](./物种树-拍板铁律.md)），转头查层级页时发现：**遗留的这条已经在线上生效了，而且走的是本文 §3.1 判为「与硬要求冲突」的那个方向。**

对照工具：`/devpages/tree-levels.html`，左栏当前实现按真实 nodeId 定位、右栏 v2 原型按 `?lv=` 同深度下钻，两栏都是活的。

**现状 = 分页。** `FAN_BATCH = 8`（`treeModel.ts`），仅 `rel===0` 分页，`placeBatchBuds` 在枝梢画「上一批 / 下一批」。§4.4 情况 3 的候选原话是「其余聚成枝端一个饱满的**芽/苞**，点芽绽开」——`placeBatchBuds` 是照这个思路写的，但落地成了一枚白色药丸按钮摆在画面正中，读作翻页控件，不是芽。

**实测各级（mock=140，竖屏 390×844）：**

| 焦点 | 分页 | 画面 |
|---|---|---|
| 界·动物界 | 1/5 | 枝端有绒球，但是**深色实心一坨** |
| 门·脊索动物门 | 1/8 | 8 根枝只有 2~3 根带绒球，其余裸线；标签只有 2 个带字 |
| 纲·鸟纲 | 1/6 | **8 根全裸线**，仅 1 根带一小簇叶；标签仅 1 个带字，余为圆点 |
| 目·雀形目 | 无 | **两根裸枝**，两个科的标签全在画面外 |
| 属·Corvus | 无 | 一片纺锤叶（机制正确，该属 mock 只收了 1 种） |

**情况 4 就是纲、目两级的常态，不是边缘案例。** 骨架切在目 → 纲下几十个目、目下科全靠收集，于是「总数超出、已收集 0~1」在真实数据里天天发生。文档当初的洞察在这里得到印证：只摆列表就是近乎空白。

**两条技术根源（渲染层，不是产品决策）：**

1. **fan 态没有总览那套补密机制。** 总览的饱满靠 `decoFillOn` 递归补出 19215 根装饰枝、把叶摊在 14860 个末梢上；fan 态里 `fanNode` 只在 `kidsAll.length === 0` 时挂装饰叶，且全部塞进 `fuzzPt(end, FUZZ * 2.2)` **一个球**里 —— 这就是「深色实心一坨」。没有装饰枝，就没有细枝分叉的结构。
2. **深层根本没有叶槽可用。** 起初以为是 `collapse` 无料可收（`backbone.json` 最高 rank=3，纲以下除收集之外空无一物）。加日志实测发现更硬的一层：**总览为了把形态写死，`grow` 里只给每节点 `ovB` 个「外沿」子枝传 `seen=true`，其余子级塌成一小截且不分配叶槽。** 层级越深越容易落在非外沿 ——

   | 焦点 | 真实子级 | 子树叶槽池 `g.le - g.ls` | 展开段 |
   |---|---|---|---|
   | 界·动物界 | 34 | 67446 | 176/1600 |
   | 门·脊索动物门 | 62 | 5760 | 41/1600 |
   | 纲·鸟纲 | 42 | **0** | **16/1600** |
   | 目·雀形目 | 2 | **0** | 5/1600 |

   纲及以下**一片叶都没有**，裸枝是必然而非偶然。而叶缓冲在 `growAll` 时已定长，事后加不进去 —— 所以补密只能走展开缓冲现补几何，而那边实测只用了 1% 的额度。

   v2 原型的假数据一路生成到种，每根末端下面本来就有子树。**v2 好看不是因为布局更好（布局常量两边逐字相同），是因为它下面有东西。**

> **结论：这条不能再往后放了。** 它是另外三个病象（裸枝、一坨球、标签大量降圆点）的共同上游 —— 情况 4 一旦有了正经表达，裸枝和绒球都有着落，标签也不必再给几十个空目硬摆。

#### 两案实现与实测（2026-09-07，过程记录 —— 结论见下一节）

> 这一节留着是因为那五个坑是**原有机制的边界**，换任何方案都会再踩；两案本身
> 已在 [下一节](#收口--展开态不按收集褪色-已拍板-09-07) 收敛掉，`?fanout=a|b`
> 这两个参数不再存在。

**共用底座 `fanFoliage`** —— 枝端现补一丛细枝、每根挂几片纺锤叶（和「种」同一套 blade 几何）。三条踩出来的实现约束：

- **不能复用总览叶槽**，理由见上表。补的是几何而不是点精灵。
- **叶要沿细枝全长贴，不能只挂叶尖。** 界级一个门有上千片点叶，只挂叶尖就摊在 4 个锚点上，还是深色实心球；放大散布半径也治不了 —— `FUZZ` 只有 2 个世界单位，再大叶就脱枝飘了。多取锚点不吃段数。
- **扇越宽，往下预览的层数越少**（`fanMaxRel`：>24 路只看 2 层，>12 路看 3 层）。改造前靠 `FAN_BATCH=8` 限流所以递归满 4 层也不过几十段；a 案把 34 个门全摆上，同样递归直接顶穿 —— 实测 1600/1600，而 `pushExpand` 超额是**静默丢弃**，表现为最后几根枝凭空秃掉，比裸枝更难查。压深度比压密度合理：34 根枝各带一层子枝加叶丛已经饱满，再往下在这个尺度上本来就糊成一片。

| | **A 满蓬成枝** | **B 一枝精描** |
|---|---|---|
| 摆哪些子级 | 全摆 | 只摆点亮的（骨架层 lvl<3 仍全摆） |
| 没点亮的 | 也长成完整的枝，整枝退向背景 `DIM_MIX=0.46` | 不占扇位，另铺一层淡枝影 `fanHaze` |
| 规模靠什么说 | 看得见的枝量 | 淡影的铺开范围 |
| 段数（界/门/纲） | 509 / 589 / 310 | 361 / 238 / 108 |

**实现中露出、已修的四个坑**（都不是方案取舍，是原有机制的边界）：

1. **标签和几何是两套挑法。** `updateLabels` 走 `batchKids`、几何走 `pickKids`，b 案下标签摆的是前 8 个目、枝摆的是点亮的那 2 个，标签就挂到别人的枝上。已统一走 `pickKids`。
2. **只靠 `COLLECT_UNLIT` 区分不出点亮。** 它把颜色往灰度均值混，而枝本来就是蓝灰的，混完几乎没变 —— 42 个空目和点亮的雀形目一个色，a 案「规模靠枝量说」就白讲了。a 案改为整枝混向**背景色**。
3. **淡影混向灰度均值等于没混**，同上。`fanHaze` 混向背景色才读作余光而非细枝。
4. **竖屏取景对「宽而扁」的扇故意允许两侧出画**（`applyFocus` 里 `aspect < 0.72` 那支）。b 案常只剩两三根点亮的枝，按满张角摆就是个大 V 字，正好撞上那条规则、两头齐齐出画，标签也被判出画而全部消失。已按枝数收窄张角（`n<=3` 时 ×0.55），淡影仍用未收窄的张角。
5. **b 案在「一个都没点亮」时只剩一根光柄。** `n === 0` 直接 return，淡影根本没机会画（实测硅藻纲 49 个目，段 1/1600）。而这恰恰是情况 4、最常见的一种。已改为 n===0 时照铺淡影 —— 那一层正是用来说「这片林子有多大」的。

**四种情况的覆盖（`/devpages/tree-fanout.html` 的「按情况」一组可直接点）：**

| # | 情况 | 代表焦点 | A | B |
|---|---|---|---|---|
| 1 | 数目刚好 | 雀形目 2 科全点亮 | 都是完整带叶的枝 | 同 A（没有未点亮的） |
| 2 | 总数超出、已收集不超 | 昆虫纲 43 目点亮 3 / 木兰纲 54 目点亮 3 | 满树，3 根着色跳出 | 3 根精描 + 40 根淡影 |
| 3 | 总数超出、已收集也超出 | **菊科 61 / 301 属全点亮**（`?wide=`） | **两案完全一样** | **两案完全一样** |
| 4 | 几乎全空 | 硅藻纲 49 目点亮 0 / 鸟纲 42 目点亮 2 | 完整的树，整体褪色 | 一丛淡影 |

**情况 3 得单开一档假数据才测得到**（`/dev/tree?wide=24|60|300`，见 `DevTreePage.wideEntries`）。原有档位造不出来，两个原因叠在一起：

- `mockEntries` 那 21 条路径是循环用的，`mock` 调到 400 也只是同一个属下多出几个种，**点亮的类群数恒定**，最宽的点亮扇只有 3。
- 骨架（真实 GBIF，rank 到目）1914 个节点里有子级的 366 个，**最宽 62**（脊索动物门），84% 的节点子级 ≤8 —— 在骨架层里怎么点亮都凑不出「一屏摆不下」。（09-07 实测口径，当时三界尚未入库；09-08 起骨架 3803 节点）

能造出来的地方只有科以下：**属和种是收集条目动态挂上去的，宽度不受骨架限制**，而那正是真实上线后会出事的地方（菊科在 GBIF 里约 1900 属）。所以 `wideEntries` 把收集挂到真实存在的菊科下，属名是编的。

**实测结论（09-07）：情况 3 里 A 和 B 完全没有差别** —— 菊科 61 属两案展开段都是 611，301 属时 A 646 / B 883（差的 237 段全是 B 给分页外那批铺的淡影）。原因很直白：**两案的分歧只在「没点亮的怎么办」，而情况 3 的定义就是全都点亮了，分歧自然消失。**

情况 3 真正的病象也不是分页本身：

1. **全点亮时标签系统崩溃。** 61 个属人人「配得上」标签，实际只挤出 4~5 个带字的、还互相压字，其余全是橙点 —— 满屏 61 颗。A 案「只给点亮的摆标签」这条在这里等于没有筛。
2. **`FAN_CAP` 兜底一跑起来就是分页。** 301 属时摆 64 根、`1/5` 页、「下一批」白药丸摆在画面正中 —— §3.1 判为与树的隐喻冲突的那个方向，原样回来了。
3. 属级枝原先是光的（属下常只收一个种，走的是 species 分支而非 `fanFoliage`）。已补：种少于 3 个的枝也补叶丛。

> **所以议题要拆：A/B 二选一只解决情况 1、2、4。情况 3 需要一套独立的折叠机制**（§4.4 原始候选里「其余聚成枝端一个饱满的芽/苞，点芽绽开」说的就是它），外加一套「点亮的太多时标签怎么取舍」的规则。这两条不该混在 A/B 的取舍里一起定。

**并排看下来 b 案暴露的问题**：真实收集数据是**链**不是树 —— 雀形目下 1 个科、科下 1 个属、属下 1 个种，只画点亮的、一路递归也只得到一根光杆。所以 b 案里「精描」的那一支同样得靠 `fanFoliage` 补体量（现规则：真实子级少于 3 个就补），否则是「一枝光杆」。**这条说明「只画收集过的东西」在当前数据密度下撑不起画面。**

**两案共同的未决项**（不在本轮改动内，需要先过方案）：

- **扇 vs 树。** 42 根枝仍是从柄末端一点放射开，读作羽毛 / 蒲扇而非树冠 —— 缺一层分叉。要做成树，得引入**分组中间层**（柄先分 5~6 根主枝，每根再带 7~8 个子级）。这是结构性改动。
- **绒球。** 界、门两级有叶槽池的地方，绒球比改造前散开了（叶贴细枝），但仍偏「花球」。
- **标签拥挤与重叠。** 界级摆了 5 个门标签就已经互相压字。见 [`物种树-3D落地与临时决策.md`](./物种树-3D落地与临时决策.md)。

#### 收口 = 展开态不按收集褪色 ✅ 已拍板 09-07

A/B 二选一没有选，**因为分歧点被取消了**。

拍板过程值得记：当时的推荐是「A 为主、保留 B 的淡影当零件」，其中一条论据是「若目不灰，A 的褪色就没有用武之地」。用户驳回了这条 ——

> 我们要的是设计目的，如果说做个方案就必须有用不就是堆屎吗？如果用户体验更好 A 方案不做就不做啊

对的。那条论据是拿「已经做出来的方案会白费」去反对一个更上游的改动，把手段当成了目的。撤掉它重新只问一句「**目该不该灰**」，答案就翻了。

**决定性的一屏是冷启动。** 之前所有对比都在 `mock=140` 下看，而新用户第一眼是空收集：

| | A（没点亮的褪色） | 不褪色 |
|---|---|---|
| 空收集 · 鸟纲 42 目 | **一整扇灰白，零标签** | 满株蓝绿，4 个目名可读可点 |
| 140 项 · 鸟纲 | 整株褪色 + 一根蓝枝 | 满树 + 雀形目带橙点与「14 项」 |

褪色是**减法**，而冷启动时一个目都没点亮，减法减掉的是整屏 —— 那不是雄伟，是荒凉。进度改由橙点、标签、「N 项」这些**加法**表达（它们本来就有），而且说得更准：褪色只能说「这些没有」，橙点直接说「这个有 14 项」。

**落地后的一套规则**（`FAN_MODE`，缺省 `on`）：

| | 处置 |
|---|---|
| 枝端补叶丛 `fanFoliage` | **留** —— 治裸枝，和灰不灰无关，是两案共用的底座 |
| 全部子级都成枝、不分页 | **留** —— 这是 A 的主体价值，治「下一批」白药丸 |
| 按扇宽压预览深度 `fanMaxRel` | **留** —— 全摆之后不压就顶穿 MAXEX |
| A 的整枝褪色 `DIM_MIX` | **撤** |
| B 的「只摆点亮的」 | **撤** |
| 「标签只给点亮的」 | **撤** —— 见下 |
| B 的淡影 `fanHaze` | **代码留，缺省不接**，挪到 `?fanout=haze` 当情况 3 的预研零件 |

**连带撤掉的一条不是颜色：标签不再按点亮筛。** 原先 A/B 都只给 `got>0 || lvl<3` 的子级摆标签（几十个空目人人一个 pill 读不了）。但既然不再拿「点亮」做取舍，未收集的目一样是**能点进去的真实类群**，藏了标签反而没法往下走。冷启动那屏因此从零标签变成几个目名可读。挤不挤得下交给标签避让判 —— 那是另一条议题。

**代码里两处 `⚠` 注释钉死了这个决定**（`fanNode` 里 dim 原址、`updateLabels` 里筛选原址），写明"别再加回来"及理由，避免下一个人看见「未收集却不灰」以为是漏了。

**实测（改动后，竖屏 390×844，段预算 1600）：**

| 焦点 | 子级 / 摆出 | 段 | 画面 |
|---|---|---|---|
| 界·动物界 | 34 / 34 | 566 | 满树，哺乳纲等带橙点 |
| 门·脊索动物门 | 62 / 62 | 757 | 满树，4 个标签带字余为圆点 |

| `?fanout=off` 对照 | 42 / 8 | 16 | 改造前，白药丸照旧 |

**总览未受影响**：几何指纹与 [`拍板铁律 §6`](./物种树-拍板铁律.md) 记录的一字不差（末梢 14860、实用叶 198792、顶点 205680 / 206016 两态）。§4.6 的 `COLLECT_UNLIT` 一行没动 —— 它往灰度均值混，在蓝灰枝上几乎不起作用，总览的灰 / 亮层次主要体现在**叶色**上，所以「展开态不灰」不需要为它另开开关。

#### 情况 3 + 标签 + 翻批 ✅ 已拍板 09-08

09-07 收口之后还欠三件事，09-08 一起定了。对照：`/devpages/tree-labels.html`。

**标签必须全留。** 降成圆点等于不可达：用户要找某一个属，满屏红点之间没有任何线索，盲点概率很大。这是翻页存在的最大理由。碰撞时纵向叠瓦错开（步长 26px、上限 ±78px），错不开就重叠；页序靠前的压在上层、点击也先落它。`?labels=old` 留着并排比改造前。

**一页 20 根。** 按竖屏「读得清」定，不是按骨架最宽 62。再多标签会把树盖住。超出才翻页。

**翻批在焦点标题左右，不在树上。** 枝梢几何芽试过：要「像树上的器官」就看不见能点，要「像按钮」就破坏树的隐喻。可发现性和植物感互斥。现方案：`‹ 前 40 个` / `还有 2 个 ›` 是标题「鸟纲」两侧的白底按钮（界面层，和面包屑同类）。字说规模不说翻页动作。树上不再画芽。

**展开态每个子级只画一根枝 + 梢上叶丛，不再递归铺下级。** 鲈形目那种大目把科/属全挤进这一根的体积，读作一团实心深蓝。展开态的任务是看清这一层、点进去；下级进焦点之后才展开。`fanMaxRel = 1`。

情况 3（菊科 301 属）因此就是「一页 20、翻 15 页、标题旁两枚按钮」。扇 vs 树（分组中间层）仍未做，另开。

### 4.5 ③ 非种级叶子 + 未归位

**(a) 非种级叶子 —— 已结案 09-03**

识别只到科时，这条收集「住」在科上。3D 树点亮这个科；照片在概要卡的「查看收集」里，点进去看。
**不在 3D 扇形上再长一片叶。** 树负责「这个分类在哪、亮不亮」，列表负责「拍到了哪张照片」。

**(b) 未归位 —— 已结案 09-03：树上不要入口**

连界都认不出的照片，不在树上做「未归位」角落。不是每张照片都要进树。
识图门槛 **已做 09-04**：`evaluateEligibility` 在 collectible 时要求 `taxonomy.kingdom.name_la`，否则 `identify_no_kingdom`，不进图鉴。旧条目不回刷。

### 4.6 点亮态 —— 已拍板 09-03，展开态那半 09-07 改判

- **界 / 门 / 纲**：不因收集变灰。即使从未收集，也显示预备好的名字（骨架中文表）。
- **目 / 科 / 属 / 种**：没收集的灰，收集过的饱和。

总览时主干和主枝仍是满色，灰的是目级末梢 —— 冷启动的雄伟感在界门纲，足迹在目以下。

**09-07 增补：以上只管总览，展开态一概不按收集褪色。**

原文那句「冷启动的雄伟感在界门纲」只覆盖了总览。**点进纲之后画面上摆的是目**，按原规则整扇全灰 —— 雄伟感在点进去那一刻就断了，实测就是一片灰白加零标签。理由与实测见 [§4.4 收口](#收口--展开态不按收集褪色-已拍板-09-07)。

两处的灰**尺度不同，不能一条规则通吃**：总览里目级末梢是小点短枝，灰读作色彩层次，也是空 / 满两态唯一的差别（用户拍板过）；展开后同一个目变成一根大枝，同样的灰就成了大面积死白。

所以分工是：**总览用灰 / 亮讲整棵树的进度，展开态用橙点、标签、「N 项」讲这一支的进度。** 展开态里的进度全是加法。

「门纲挤成圆点」是标签放不下，和灰置不是同一件事。

预备名字不全就显示拉丁名，不再补表。这和灰置不是同一件事。

「门纲挤成圆点」是标签放不下，和灰置不是同一件事。
**2026-09-03：** 圆点取舍整套机制用户不喜欢（门多时大量圆点、名字忽隐忽现）。
根因：碰撞就降成圆点；展开时镜头还在微晃，每帧重算谁留下，于是闪。当大问题，先不另做一套。

### 4.7 树冠布局 = 写死三档高度 + 动物/植物各拆两支 ✅ 已拍板 09-04

代码：`apps/web/src/tree/TreeScene.ts` 的 `CANOPY` / `TIER_LEN` / `growForked()`。

**① 高度写死三档，不随数据浮动。**

| 档 | 类群 | 枝长（主干高的倍数） | 起点 |
|----|------|--------------------|------|
| 高 | 动物、植物 | 0.72 | 主干顶 |
| 中 | 真菌 | 0.62 | 主干顶 |
| 矮 | 色藻、原生动物 | 0.20 | 主干 0.70 高 |

档内再加 `hash(节点ID)` 的 ±8% 扰动，避免同档几根一模一样长（§4.3 的延续）。
**关键是「不随子级数量浮动」** —— 原来按节点数定长短，数据一变形态就跟着乱。

**② 动物、植物各拆成两支主枝，且两支相邻。**

34 个门全挂一根枝上会粗得像根柱子，没有大枝杈的体量感。做法是：
界画成「一短柄（0.30L）+ 两根次主枝（0.76L）」，门平分到两支上。

- **纯几何，数据结构不变。** 次主枝没有对应节点，顶点写在本界的 `[vs, ve)` 区间内，
  `collapse` / `fanReset` / 焦点隐藏都会连带处理，不需要为它加任何分支逻辑
- **两支必须相邻**（`CANOPY` 表的书写顺序保证），同色成簇才读得出「这是一个界」

**③ 枝位是全树共用的角度刻度，拆枝的每一支各占一位。**

动物 2 + 植物 2 + 真菌 1 = 5 个枝位，圆周上 72° 等分。矮枝插在枝位的空隙里
（枝位在 `(k+0.5)·gap`，空隙就在 `k·gap`），才不会被大枝正面盖住。

> **踩坑记录**：第一版按「界」分角度、两支挤在同一枝位附近张开，结果 5 个枝位
> 只用了 3 个方向，树整个偏向一侧。必须按**枝位**而不是按**界**分配角度。

**④ 连带删除 `grow()` 里 `isBasal` 的几何特例。**

`isBasal` 原本让子级 `spreadK ×1.45` 且**全部强制外沿满长**，那是为「贴地矮丛」写的。
色藻/原生动物进树冠后这套仍在生效，把它们撑成了两个蒲公英球。删掉后
basal 的几何与 crown 完全一致，只保留颜色上的轻度淡化。

## 5. 渲染实现的经验值（防止重复踩坑）


外观调整基本只需改参数，但以下几个参数**极其敏感**，改动前先读这里：

| 参数 | 教训 |
|------|------|
| `decay`（枝长衰减） | 这是 6 层复合的**指数**。0.68 → 0.755 会让末端枝长翻倍，**单个界就能撑爆整个画面**。0.70~0.74 是平衡区 |
| 枝的宽长比 | 应在 **0.03~0.06**，真实树枝就在这个范围。到 0.14 就是一根棒子。改长度后必须同比改宽度 |
| `photo`（趋光偏置） | 树冠必须**由正转负**（内层上举、外缘下垂），冠才是圆的。全程为正 → 所有枝互相平行 → 冠顶压平、下半空掉 = 「沙漠合欢」 |
| `spread`（分叉角） | 只有 3 根主枝要填满 360°（不是 6 根），每支张角必须更大 |
| 子级绕枝方位 | **必须均匀分布 + 小扰动**。纯黄金角螺旋只在数量多时才均匀；每节点只有 3~5 个子级时螺旋会把它们堆在一侧，逐层放大后整棵树偏心 |
| 子级分叉位置 | **必须沿父枝全长错落分出**。若都从父枝末端一点爆开，每个节点会长成独立的球，整棵树成了「三叉戟挂三个球」，球之间必然空 |
| 地面散点半径 | 铺得比树冠还宽会变满屏噪点，且俯视下远处地面会投影到画面上方、把根系淹掉。噪点要靠**降低着色**压制，不是缩小面积 |
| 包围盒 | **必须统计叶点**，不能只算枝顶点 —— 叶簇长在枝端之外，只算枝会低估树的范围，取景必然溢出 |
| 根系「广」 | 加长根枝会又宽又深。正确做法是**把方向的竖直分量压扁**（×0.30），长度全部转化为水平延展 |
| 叶点形状 | 实心圆 sprite 放大后就是一堆小球。解法：fragment 里**按每点 seed 旋转 UV**画细长叶片，并按屏幕尺寸在「柔边圆点（远）↔ 叶片（近）」之间过渡。（点精灵本身无法旋转，但 UV 可以旋转 —— 我曾误判为不可行） |
| 展开层段数 | 大树缓冲给深层枝只分 2~4 段（总览时只占几像素），展开后放大到半屏就是折线。需要**单独一套 10 段的展开缓冲**（~600 根枝，4MB），不能全局提高段数（要 59MB） |
| 深入态的雾 | 会叠加在叶点自身的提亮上，把颜色洗成灰白。`uFogK` 展开态要压到 0.3 左右 |
| 隐微感 | 要靠**去饱和**，不能靠提亮 —— 提亮会把根系洗成白色，在浅底上彻底消失 |

**主干必须直立**：`axialOut` 里 `A[0] || fallback` 的写法，在主干（起点 `[0,0,0]`）
上会因 `0` 是 falsy 而走 fallback 分支，把主干强行推向 +X，整个树冠随之偏心。
