# WIP 目录 · 使用与清理原则（元文档）

> 本目录是**施工区**，不是文档区。完工的东西不该留在这儿。
> 本文只讲三件事：什么该进来、什么时候该走、走的时候往哪儿并。
> 真源永远是 [`SPEC.md`](../SPEC.md) 与 [`docs/features/`](../features/) 下的正式文档。

## 1. 什么进 WIP

| 种类 | 例 | 归属 |
|------|-----|------|
| 施工备注 | 分段施工记录、拍板记录、临时决策表 | 收口后清空 |
| **正在做 / 未落地**的方案 | 宠物副轨（D1–D6c 已拍板但未实现） | **留 WIP，不进正式文档** |
| 长期议题 | 物种树结构议题 | 讨论完再定 |
| 原型 / demo | 被代码注释引用为视觉基准的 | **参照物，长期保留**（见 §5） |

## 2. 什么不该留（进了也要走）

- 已经落地的功能说明 → 并入 features 对应文档（§4）。
- 一次性事故记录 → 结论固化进 [`OPS.md`](../OPS.md) / 正式文档后删。
- 已实现功能留下的施工过程 → 直接删（踩坑史没有长期价值）。

## 3. 什么时候清理

判据是**落地状态**，不是拍板状态。已拍板但还在施工的，仍然留 WIP。

> **保守原则（重要）**：AI 判断"这个功能完成了" ≠ 可以清理。
> 合并 + 删除必须由**用户确认完成**后再做。自认为完成了可以先问："X 是不是算完成了？能并进正式文档吗？"——用户说完成了才动手。
> 理由：误删/误并的代价（丢信息、埋错误描述）远大于多留一份 WIP。不确定的一律留着。

| 状态 | 动作（经用户确认后） |
|------|---------------------|
| **用户确认已完成 / 已收口** | 并入 features 对应文档（§4）→ 删 WIP 原件 |
| **用户确认过时 / 被否决** | 结论有价值就并入正式文档，否则直接删 |
| 正在做 / 未落地 | **留着，不进正式文档** |
| 参照物（原型 / demo） | 长期保留，不清理（§5） |

## 4. 往哪儿并（归宿对照）

**先找 features 里有没有同主题文档——有就并进去，不新建同名或近义文档。**
features 里完全没有的主题，等它落地后在 features 新建，不是继续留 WIP。

| 主题 | 正式文档 |
|------|----------|
| 识图 / 三档（相遇·未相遇·留影）/ 软档 / 配额 | [`features/识图护栏.md`](../features/识图护栏.md)（+ [`SPEC.md`](../SPEC.md) §1.2） |
| 皮肤 / 主题 / 动效 / 创作动作 / 前端设计原则 | [`features/皮肤主题.md`](../features/皮肤主题.md) |
| 物种树（铁律 / 结构 / 渲染） | [`features/物种树.md`](../features/物种树.md) |
| 套册 / 成就 | [`features/旅行套册.md`](../features/旅行套册.md) |
| 共享旅途 | [`features/共享旅途.md`](../features/共享旅途.md) |
| 运维事故 / 部署 | [`OPS.md`](../OPS.md) |
| 全局规格 / 行为摘要 | [`SPEC.md`](../SPEC.md) |

## 5. 合并时怎么消冗余（最容易出错的一步）

合并不是"把 WIP 复制一份贴过去"，是**改已有文档**。

- **同一功能只留一处描述。** 不要追加一段"新版"让新旧并存——那等于埋了一处错的。
- **过时的句子要改掉，不是留着。** 例：识图护栏原写"`unclear`、人、玩具一律拦死"，实际已改三档就该删掉这句。
- **旧描述与新实现矛盾时，以代码现状为准**，把错的改对。
- 顺带扫一遍：SPEC 等上层文档里可能也有同一功能的旧摘要，一起改。

## 6. 参照物：留文件，但代码注释不许引它

被代码或文档注释引用为视觉基准的原型 / demo / 基线图，是**参照物**不是临时稿，**文件本身长期保留**。

- 先例：物种树铁律 §6「参考版本长期保留」，理由是防"做出来天差地别还无处追责"。
- 当前实例：`settle-rarity-spotlight-demo.html`（开包四拍节奏的出处）。

**但代码注释里不许引用 WIP 路径**（见 §8）。参照物留着供人对照，代码只指向正式文档。

### 判别：它到底算参照物还是临时稿？

问一句：**删掉它，还能不能追责 / 复现现在的实现？**

- 能替代（只是当初的草稿，实现已完全独立）→ 临时稿，走清理。
- 不能（实现是从它身上抄的、或它是唯一记录）→ 参照物，保留文件。

## 7. 每份 WIP 的开头要声明性质

新写 WIP 时第一行写清楚：性质（施工备注 / 方案 / 议题）+ 时效 + 真源在哪。
好例子（宠物副轨开头）：

> 性质：施工备注，不是功能真源。查正式规格仍以 `SPEC.md` 为准；一段收口后结论写回正式文档再清空对应段落。

这样接手的人不用读完就知道它该不该信、什么时候该走。

## 8. 代码注释只引正式文档（铁律）

**代码注释里不出现 `docs/wip/` 路径。** 注释要引文档，就引 `docs/features/`、`SPEC.md`、`OPS.md` 这些正式文档。

理由（用户 2026-09-09 拍板）：

> "最好是代码注释在完全体引用正式的功能文档。记忆是不可靠的，该写文档里还得写——不止你一个 agent 工作这个目录。"

展开：①WIP 会删，注释里的路径会变死链；②下一任 agent（或另一个 AI / 同事）读代码时，只会去看注释指向的地方，**不会知道该内容其实已迁走**；③记忆 / 会话上下文不跨 agent 共享，判据必须落在文档里。

**处理办法**（WIP 里的议题还没落地、正式文档没法写时）：

| 情况 | 怎么做 |
|------|--------|
| 议题已落地 | 注释改指 `docs/features/xxx.md` 对应小节 |
| 议题还在讨论、正式文档写不了 | 注释里**写清结论本身**（参数、口径、为什么），不写"见 wip/xxx" |
| 确实需要指向讨论过程 | 用**不带路径**的说法，如"见物种树结构议题 §4.4"，并在正式文档里留一节承接 |

**先例**：`treeModel.ts`、`export-backbone.py` 原引 `docs/wip/物种树-拍板铁律.md`，铁律迁进 `docs/features/物种树.md` 后注释已改指新位置。

### 清理时的收尾动作

- 合并完 WIP，**全局搜一遍 `docs/wip/`**，把代码 / 文档注释里的引用改指正式文档。
  ```powershell
  rg "docs/wip/" -l
  ```
- 删之前确认：内容已在正式文档里（不是"打算写"），或被明确否决且无保留价值。
- 不确定的，留着，别删。删错比多留一份代价大。

## 9. 这个目录不止一个 agent 在用

同一个 WIP 目录会有多个 AI agent / 人轮流工作。**不要依赖"上次那个 agent 知道"**——记忆不跨 agent 共享。

- 判据、结论、状态一律写进文档，不留在会话里。
- 动了 WIP 或正式文档，开头 / 结尾带上日期与依据（谁拍板、在哪拍的）。
- 读到一份 WIP 不确定它是否还有效 → 看它的声明（§7）+ 对照代码现状，别猜。
