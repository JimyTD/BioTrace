## 1. 骨架数据

`apps/web/src/data/backbone.json` —— **1914 节点，130KB → gzip 21.4KB**，内置不查库。
重新生成：`python scripts/export-backbone.py`

### 临时决策 A：只导「用户会去的地方」

| 分区 | 类群 | 数据 |
|---|---|---|
| 树冠 | 动物 / 植物 / 真菌 | **真骨架**（界→门→纲→目） |
| 近地 | 色藻 / 原生动物 | **真骨架** |
| 根系 | 细菌 / 古菌 / 病毒 | **假枝丛**（hash 生成，不可点） |

根系用假的，三个理由（前两个是实测发现的）：

1. 真骨架里根系 **1886 节点 > 整个树冠 1429**，会压倒主角
2. 名字是 `UBA10199` / `JACPQU01` 这类宏基因组代号，没有可读性
3. 用户永远不会点进去

**副作用（好的）**：去掉根系后最大扇出从 **171 降到 62**，不再需要为极端扇出做特殊处理。

> 万一真拍到蓝藻水华：条目自带完整 taxonomy 路径，会在假枝丛里长出一根真枝，不依赖骨架数据。

### 临时决策 B：中文名只覆盖高阶元

`apps/web/src/data/backboneZh.ts` —— 280 条。**界 100% · 门 100% · 纲 28% · 目 7%**。

GBIF 的高阶元中文名覆盖率是 **0%**（实测：`Aves` / `Mammalia` / `Passeriformes` / `Carnivora` 全无，只有 `Felidae`→「貓科」且是繁体）。所以必须自备。

不全量覆盖是遵守工程既有原则：「没有通行中译时 `name_zh` 必须为 null，禁止臆造」（`apps/api/src/identify/prompt.ts:65`）。没覆盖的显示拉丁名 —— **「你走过的地方有中文名，没走过的地方是拉丁文」本身就是诚实的表达**（用户自己的条目自带 AI 给的中文名，不依赖这张表）。

> ⚠ 改这张表必须跑 `python scripts/check-zh.py`。死键（骨架里不存在的键）永远不会命中，界面上静默显示拉丁名，肉眼发现不了 —— **我第一版就写错了 17 个**。

### 三个必须记住的数据真相

> 性质不同，别混为一谈：① 是**与文档明确断言冲突**；②③ 是**实现时的坑**（原设计并未假设相反的事）。

**① 文档 §4.1「目级以上扇出 ≤40」是错的。** —— 真冲突。
实测扇出 >40 的有 6 个，最大 `Chordata` → 62 纲/目。

**② 同一个父节点下，子级的 rank 可以不统一。** —— 不是设计冲突，是渲染与文案的坑。

GBIF 没有 `Reptilia`（爬行纲），也没有 `Actinopterygii`（辐鳍鱼纲）：

```
Chordata（脊索动物门）的 62 个子级 = 16 个纲 + 46 个目
├── Mammalia       纲
├── Aves           纲
├── Squamata       纲   ← 有鳞，教科书里是「爬行纲的目」
├── Testudines     纲   ← 龟鳖
├── Cypriniformes  目   ← 鲤形目，鱼类没有纲那一级，目直接挂在门下
└── Perciformes    目
```

全骨架里子级 rank 不统一的父节点共 **16 个（占有子级节点的 4%）**，
但 `Chordata` 恰好是最重要的一支（脊椎动物全在里面）。查证：`python scripts/probe-mixed-rank.py`

**实际影响（已修）**：概要卡曾按「子级阶元 = 自己 + 1」写死，
点脊索动物门会显示「62 纲」—— 在说谎。现在按子级实际 lvl 分组，显示「16 纲 46 目」。

**顺带的坑**：中文名表不能按教科书常识填。我第一版写了 `2:Reptilia`、`3:Squamata`，
骨架里实际是 `2:Squamata`。`check-zh.py` 就是为此存在的。

**③ 拉丁名在同一界内会重复** —— 也不是设计冲突，是 id 方案的硬约束。

真实的生物学现象（单型分类单元）：

```
Diplura 纲 ← Arthropoda      「双尾纲」
Diplura 目 ← Diplura(纲)     「双尾目」，父是同名的纲
```

所以节点 id 必须是 `rank:拉丁名`，否则节点会**自己当自己的父级 → 建树成环**。
同类还有 `Protura`、`Micrognathozoa`、`Dothideales`。这条也决定了 URL 不能用拉丁名路径链（见决策 D）。

## 2. 架构

```
tree/treeModel.ts    骨架 + 收集 → 一棵 TreeNode 树（纯数据，无 DOM）
tree/geom.ts         向量数学 + 界的视觉定义（颜色 / 三段式分区）
tree/TreeScene.ts    WebGL 场景，框架无关（canvas + 标签 DOM 池 + 每帧更新）
components/SpeciesTree3D.tsx   React 宿主：概要卡、详情视图、面包屑、URL 同步
pages/CollectionTreePage.tsx   页面：数据加载 + 路由
pages/DevTreePage.tsx          dev 预览（绕过登录/API）
```

### 临时决策 C：标签不用 React 渲染

标签每帧都要改 `left/top`，走 React 会每帧触发 reconcile。`TreeScene` 直接操作 96 个 DOM 池元素。概要卡用 React —— 它不是每帧更新的。

### 临时决策 D：URL 用单节点 id，不是路径链

```
/collection/tree              全树
/collection/tree/2%3AAves     聚焦鸟纲
```

旧实现是拉丁名链（`/tree/Animalia/Chordata/Aves`）。改的理由：

- 3D 树的展开只需要焦点，父链能从数据推出（`chainOf`）
- **骨架里拉丁名会重复，链式路径无法消歧**（见数据真相 ③）
- 链会很长，而 3D 树本来就靠场景本身表达「我在哪」

焦点变化只改 URL 参数，`SpeciesTree3D` 不卸载 → **WebGL 上下文保住，展开是连续 morph**。深链、返回键、前进后退全都免费拿到。

## 3. 视觉参数：真实骨架把原型的假设打破了三处

原型有 6 层（界→属），真骨架只有 4 层（界→目）。层数少两级，**末端枝长差近 2 倍**，凡是「按枝长 L 算」的参数全部失真。

| 参数 | 原型 | 现在 | 为什么 |
|---|---|---|---|
| 叶点尺寸 | `L * 0.105` | `TRUNK_H * 0.0135`（绝对） | 按 L 算会让叶点又大又散，整棵树成了一团气泡，相邻界的叶簇互相侵入（动物界压掉植物界） |
| 叶簇半径 | `L * (0.26~0.56)` | `L * (0.10~0.21)` | 同上。压紧后叶才是「附着在枝上」而不是飘在周围 |
| 装饰叶数 | — | 门 30 / 纲 40 / 目 58 | 骨架比原型少两级分叉，末端枝少得多，要每枝多挂叶才凑出雾状树冠 |
| 近地侧枝长 | `TRUNK_H * 0.30` | `TRUNK_H * 0.17` | 真骨架色藻界 344 节点 ≈ 植物界 307，给同样枝长就长成和树冠一样大的球，像另一棵树 |

### 临时决策 E：装饰性叶簇（机制 2 的落地）

骨架只到「目」，目下面没有真实节点 —— 不加装饰叶的话树冠是一把光秃的枝，而**雄伟感恰恰来自海量叶点**。

叶数由节点 id 的 hash 定，所以**形态恒定**：同一个目永远长成同一个样子。「假」不等于「随机」—— 每次打开都变样是不能接受的。

按你的要求**不显示「还有 N 属未探索」**，所以「科→属数」的数据成本一并消失（不用内置表、不用调 API）。

## 4. 标签策略：混合

### 临时决策 F：界用「推开」，其余用「降级」

| 层级 | 策略 | 依据 |
|---|---|---|
| **界**（8 个，固定） | 碰撞就上下交替推开，**永不降级** | 只有 8 个（推得开），且总览时是唯一路标，降成圆点就没法认路 |
| **其余** | 碰撞就降级为一个小圆点 | 数量不定且可能很多（62 纲），推不开 |

降级态是地图的做法：缩小时地名消失但地点标记还在。点圆点出概要卡，**信息没丢，只是从常显变成按需**。

> 这条是在原型里实测定下来的：旧的「碰撞就 y+=54 往下顶」在 16 个子级时就会叠成一竖列、脱离自己的枝、盖住整棵树。标签需要 N×54px 竖向空间，而枝丛只占屏幕中间约 250px，**差 3.5 倍**。

排序优先级：**有收集的优先** → 靠近画面中心的优先。所以你的足迹永远有名字。

### 临时决策 G：副标只写收集数，不写阶元

中文名本身已带阶元后缀（动物界 / 脊索动物门 / 鸟纲 / 雀形目），旁边再标「界」「门」是纯冗余。没有收集时留空，让画面安静。

## 5. 手机适配

### 临时决策 H：总览做水平压缩，展开不做

这棵树宽大于高（三主枝 360° 铺开）。手机竖屏 `aspect≈0.46` 时宽度成取景瓶颈 —— 相机被迫拉远，树只占屏幕中段，上下全空。

在投影矩阵右边插 `diag(sq,1,sq)`，把 X/Z 压到「宽度刚好不再是瓶颈」：

| 视口 | `SQ` |
|---|---|
| PC 1440×820 | **1.00**（零改动） |
| 手机 393×852 | ≈0.62（瘦高，竖向铺满） |

三个让它成立的细节：只压位置不压枝宽（枝宽是屏幕空间的）；标签走 `project(世界点, VP)` 自动跟随；**只作用于总览态**，随 `morph` 插值到 1 —— 展开是「凑近看一支」，取景本来就按包围盒自适应，再压只会让扇形变空。

语义上也对：真实的树密林里瘦高、旷野里宽展。

### 临时决策 I：竖屏收窄展开扇形的张角

扇形横向铺开，竖屏下横向仍是瓶颈 —— 实测 34 个门展开后只占屏幕 1/3。

竖屏时张角 ×0.62、子级枝长 ×1.34（补回收窄损失的铺开感），宽屏 ×1.0 不变。

## 6. 详情视图

### 临时决策 J：不新增路由，同层换呈现

概要卡的「查看收集」在**同一个页面内**推出详情视图（`.tree3d-sheet`），不 `navigate`。

这是「3D 看结构 / 列表看收集」的分工 —— 同一层数据的两种呈现，不是两个地方。复用现有路由，返回时 3D 场景保持原位（WebGL 上下文没销毁）。

**顺带化解了「非种级叶子」**：识别只到科的条目就出现在科的详情里，3D 树不必特殊表达同一层既有枝又有叶。

### 未做：未归位（unplaced）

连界都没识别出来的条目，`treeModel.ts` 里直接 `return`（不上树）。按之前讨论应该是一个固定 UI 入口（角落「未归位 N 项」）直接进详情页 —— **还没做**。

### 修过的（记下来免得再犯）

- **概要卡说谎**：按「子级阶元 = 自己 + 1」写死 → 脊索动物门显示「62 纲」。见数据真相 ②

### 11.4 三条不要轻易推翻的设计

| 设计 | 为什么 |
|---|---|
| **节点 id 带 rank**（`2:Aves`） | 拉丁名在界内会重复，去掉 rank 会导致建树成环。见数据真相 ③ |
| **标签直接操作 DOM 池，不走 React** | 每帧改 `left/top`，走 React 会每帧 reconcile |
| **URL 只存焦点 id，不存路径链** | 父链能从数据推出；且拉丁名重复使链式路径无法消歧 |
