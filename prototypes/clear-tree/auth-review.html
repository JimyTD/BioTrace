一、同一句话占两条 key · resetOk / passwordChanged

zh.ts:29,40 · 服务端 auth.ts:244（邮件重置成功）· auth.ts:359（登录后改密码成功）

现状 · 两条 key，一个字不差
重置成功：密码已更新
改密成功：密码已更新
两条 key 承担的是同一句话，只是从两条不同的服务端路由返回（重置码流程 / 登录后改密）——没有信息增量
建议 · 合并成一条
两处都用 auth.passwordChanged「密码已更新」
删 auth.resetOk，auth.ts:244 改指 auth.passwordChanged（规则 7：不为分型写多套 key，除非有信息增量）

二、「请输入」/「请填写」混用

zh.ts:30,31,34,38 · 四条同类校验提示

现状
invalidEmail　请输入有效邮箱
invalidRegister　请填写有效邮箱，密码至少 8 位
invalidReset　请填写邮箱、6 位重置码，新密码至少 8 位
invalidPasswordChange　请填写当前密码，新密码至少 8 位
四条是一模一样的场景（表单校验失败），却用两个动词
建议 · 统一到「请填写」（3 : 1）
invalidEmail　请填写有效邮箱
其余三条不动
改一条就齐了；反方向要改三条

三、兜底句说错了动作 · auth.failed

zh.ts:17 · 渲染点 LoginPage.tsx:100（提交失败）· :114（开发登录失败）

现状
注册时抛非 Error：登录失败
重置时抛非 Error：登录失败
同一个兜底被登录 / 注册 / 重置 / 开发登录四种提交共用，文案却只说「登录」。
触发条件是「抛出的东西不是 Error」（正常不该发生），此时才回落到它；平时显示的是服务端的 err.message。
建议 · 改成中性一条
auth.failed：操作失败，请重试
不为四种提交各写一条（规则 7）；中性说法在四个场景都成立，且补了「重试」这个出路

四、同一动作两个词 · registerAction / registering

zh.ts:20,21 · 渲染点 LoginPage.tsx:241（入口链接）、:128（提交按钮）、:127（加载态）

现状
创建账号忘记密码下载 App
创建账号
点下去之后按钮变成：注册中…
入口和按钮都叫「创建账号」，一点下去变成「注册中…」——同一动作两个词（创建 / 注册）
建议
创建账号忘记密码下载 App
创建账号
加载态改成：创建中…
改 auth.registering「注册中…」→「创建中…」，与按钮同词；按钮名不动（它同时是登录页的入口链接）

五、存疑两处（我不擅自动，你定）

存疑 ① · auth.invalidProfile「昵称无效」
它兜的是两种校验失败：昵称超过 40 字，或请求没带任何可改字段（后者是客户端 bug，用户看不到）。
按「能据此行动吗」该补规则（如「昵称不能超过 40 个字」），但补细了会在第二种情况下说错。我倾向不动——它是兜底的兜底，说粗反而安全。
存疑 ② · auth.forgotPassword「忘记密码」同时是两个岗位
它既是登录页的入口链接（LoginPage.tsx:249），又是重置模式的页头 lede（:137——正常那里显示的是 app.tagline 品牌句）。
也就是说：品牌句的位置在重置模式下被一个功能性标签顶掉了。我倾向不动——重置模式下用户确实需要一个「你在哪」的标题，而页头是唯一的位置；拆成两条 key 只是为了不让一个 key 干两件事，不带来信息增量。
