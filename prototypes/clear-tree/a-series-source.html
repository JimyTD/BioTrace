二、全文（8 节，逐条）

为什么需要基准
  • 灯箱 voice 当年把「相册」改「一卷」，册族与卷族混搭出缝 → 所以要有尺子
  • 管两件事：① 基底文案（zhFlavor 43 key）自己先合格 ② 未来 voice 覆盖表评审时有对照
一、人称与称谓
  • 对用户一律「你」，禁用「您」
  • 对生命一律「它」
  • 不出现昵称化（「小家伙」「这位」）
二、句式
  • 黄金句式：现状句 + 行动句（trips.empty 为样板）
  • 界面句 = 两个短句上限；单句静态字 ≤ 14 字，超了拆句或移固定区
  • 仪式句允许 · 分隔，不按散文句法审
  • 句号收尾，禁感叹号；toast 可无标点
  • 疑问句只在真提问时用，不用反问装饰
三、五大隐喻家族（白名单）
  • 册族：翻开 / 册页 / 整册 / 第一页
  • 证书族：鉴定证书 / 请过目 / 收下
  • 点亮族：点亮 / 一格 / 整册点亮
  • 落点族：落点 / 足迹 / 点
  • 专家族：专家鉴定中 / 专家只敢认到大类 / 专家歇了（固定区）
  • 跨家族混搭出缝是灯箱时代的教训，禁止
四、术语口径
  • 树上统一「收录」；nav 仍叫「图鉴」
  • 量词：点亮族「格」、册族「本」、树上「项」
  • 「项」vs「种」：保留「项」不冒充「种」
五、第三区（人格区）——未实施
  • 为专家家族文案预留 PersonaKey + 锚词校验；触发条件写死：第一套叙事皮肤立项时启用
六、lint 边界（机器管什么）
  • 只拦：感叹号 /「您」/ 静态字超 14 / 家族组 key 存在性 / voice 占位符保全；文采、节奏、意境一律人评
八、新增文案两条硬约束（2026-09-10 用户拍板）
  • 一、先查能不能复用 common，不许直接新建
  • 二、不做无意义兜底；判定口诀：这个分支用户真能看到吗？看到了会做不同决定吗？
七、本次整改台账（2026-09-07）
  • auth.registerLede 降固定区 / me.appearanceLede 拆分 / 收集→收录 / 公文腔→仪式语感 等 11 条

三、我的读法：为什么说它是「错误」不是「带偏」

  • 来源不可追溯。挂着「用户拍板的总策划方案」，却查无此方案。规则是 agent 写的，名头是借的。
  • 把发明写成硬规格。「≤ 14 字」「黄金句式」「五大隐喻家族白名单」都是自造概念，却被 check-voice.py 当机器闸门执行——从此不可违背。
  • 自造框架锁死表达。「禁止跨家族混搭」把一个自造的词汇表变成了牢笼。
  • 体系内自相矛盾。它写「句号收尾」，后来的纪律写「尽量不用句号」——同一套体系里两条打架，说明它不是从统一认识来的，是逐条堆出来的。
